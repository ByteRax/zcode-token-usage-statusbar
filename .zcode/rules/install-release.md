# 安装、注入、更新与发布链规则

适用路径：`install.py`、`patch_install.py`、`install_monitor.py`、`plugin-updater.cjs`、`plugin-release.cjs`、`plugin-storage.cjs`、`runtime_lock.py`、`release_unpack.py`、`release_tool.py`、`sync_plugin.py`、`plugins/zcode-token-usage-statusbar/` 下的 `overlay_install.py`、`plugin_auto_update.py`、`restart_notice.py`、`hooks/`、两份 manifest、`marketplace.json`，以及对稳定运行目录 `~/.zcode/zcode-token-usage-statusbar/` 的任何部署操作。

发布流程本身以 [docs/maintaining.md](../../docs/maintaining.md#发布插件) 与 [发布技能](../skills/zcode-github-release/SKILL.md) 为准；本文件记录链路契约与陷阱，根 [AGENTS.md](../../AGENTS.md) §3、§8 是其摘要。

## 1. 分发文件登记（新增/改名文件必查）

一个文件进入分发链要同步**全部**登记处，漏任一处都会在不同阶段报错或断升级（`python3 sync_plugin.py --verify-manifests` 及 `python3 sync_plugin.py --check` 会自动交叉校验以下 6 处登记，并在同步前自动调用 `scripts/build_overlay.py` 与 `scripts/build_quota.py` 拼接生成根 `overlay.js` 和 `quota-client.cjs`）：
- `sync_plugin.py` 的 `FILES`（根→插件副本同步）与 `release_tool.py` 的同步清单；
- `release_unpack.py` 的 `PLUGIN_FILES`（安全解包文件集）；
- 两份运行清单的 `RUNTIME_FILES`（`overlay_install.py` 插件链与 `install.py` 独立链各一份，都拷到稳定运行目录：注入行指向运行目录，`inject-main.cjs` 相对 require 的每个本地模块及 `zusage.py`/`token_rate.py` 共用的 `usage_stats.py` 都必须在列，否则模块静默缺失只在加载时报错；`test_plugin_package` 对两份清单按此不变量守护）与 `overlay_install.py` 的 `cold_files`（决定哪些变更要求完全重启）；
- `restart_notice.py` 的 hashes 名白名单（漏改报"提醒记录 hashes 无效"）；
- 两份 manifest（`.zcode-plugin/plugin.json`、`.claude-plugin/plugin.json`）的 `packageLayout.files`——在野旧版解包器要求文件集精确声明，漏声明会让旧版无法升级到新版（曾两次事故），`release_tool.py build` 的 `require_layout` 与 `sync_plugin.py --verify-manifests` 会拦；
- 相关契约测试（`tests/test_plugin_package.py`、`test_plugin_runtime.py`、`test_release*.py`）。

反向也要成立（仅指插件链）：`usage_mcp.py`、`mcp-launch.cjs`、`overlay_install.py`、`plugin_auto_update.py`、`restart_notice.py` 与 `hooks/` 下的入口在插件链都从插件目录（缓存）运行，import 的兄弟文件同样来自插件目录，**不属于** `overlay_install.py` 的 `RUNTIME_FILES`，不要为「看起来同步」把它们加进运行时目录；`install.py` 独立链是例外——它的 `RUNTIME_FILES` 必须含 `usage_mcp.py`（独立链的 MCP 从运行目录运行）。

## 2. 注入与运行目录

- 插件缓存按版本号换目录，而 asar 注入行是绝对 `file://` URI——所以 loader 必须先复制到稳定运行目录再对该目录注入，此后升级只需同步文件即可热更。注入/安装时把 `sys.executable` 绝对路径写回配置 `python_path`，每次 SessionStart 刷新。
- asar 原子替换（mkstemp → `os.replace`）后必须 `os.chmod(stage, S_IMODE(原 asar mode))` 保留权限位，否则降成 0600（lifecycle 测试断言 0644）。探测 `/Applications/ZCode.app` 等系统路径（如 `patch_install.py` 的 `ui_element_exe_for`/`syntax_check` 与 `renderer_bridge.py` 的 `_output_path`）必须用 `_safe_is_file` 或捕获 `OSError`（含 `PermissionError`）：Python 3.8/3.9 在受限沙箱或 TCC 拦截下调用 `Path.is_file()`/`is_symlink()`/`resolve()` 会直接抛 `PermissionError` 而非返回 `False`。
- 待收尾包（pending TMP）的常驻收尾者是 `install_monitor.py`；无人值守的孤儿 pending 有三处补救：插件链 SessionStart hook 的自动安装、hook 的 `_revive_orphan_pending` 自愈检查（合法 pending + 实例锁空闲 + 目标可写 ⇒ 补拉静默监控，issue #228；目标可写前置守住 issue #130 受保护目录边界），以及 `usage_mcp.py` 进程启动时的 `revive_finalize_monitor()`（独立链无 hook，MCP 是其唯一会话级入口；config 所在目录即运行目录，收尾来源授权以此对齐 sidecar）。`_publish_pending` 的 journal 中间态（`cancelled`+`publishing`，期间全量 hash 大包，秒级窗口）是瞬时态：`pending_tmp` 对它抛 `PendingTmpBusy`（`PendingTmpError` 子类），监控循环必须重试续守，绝不能按「来源失效」退出让位——旧监控退出 + `launch_monitor` 去重跳过新拉起 = 孤儿 pending，重启不再替换（issue #228 根因）；`pending_operation()` 对 journal 仍返回 `cancelled`，复活/让位判定因此天然跳过发布窗口。两份运行清单的 `RUNTIME_FILES` 都必须携带 `patch_install.py`/`install_monitor.py`/`runtime_lock.py`——失败提示里的手动收尾命令只依赖运行目录内这套脚本，缺任一个，clone 删除后命令即不可执行（issue #163；`test_standalone_runtime_files_cover_finalize_toolchain` 守护）。
- **Windows 手动安装必然「运行中替换失败」，属预期**：`/install-overlay` 总在运行中的 ZCode 内执行，客户端占用 `app.asar`，`os.replace` 以 `[WinError 5]` 拒绝；收尾全靠监控等完全退出。因此**可见监控也必须活过宿主回收**：`launch_monitor` 可见分支 breakaway 被拒时改走与静默分支共用的 `_spawn_survivor_monitor`（WMI + pythonw + `--quiet`，无窗口），都不可用才回树内可见监控；改这两条拉起路径要同时改 `tests/test_quiet_monitor.py` 的可见/静默用例，且可见模式的说明文案只许走可见分支（静默模式服务 hook，stdout 不夹文本）。规格见 [specs/windows-visible-monitor-survival.md](../../specs/windows-visible-monitor-survival.md)。
- 参与 INJECT_LINE 字节比对/自检的 `--runtime` 路径禁止 `Path.resolve()`（macOS `/var`↔`/private/var` 符号链接会破坏字面比对），只用 expanduser/expandvars/abspath；`--asar` 可完整 resolve；standalone `install --finalize` 在自定义安装路径需同时给 `--asar` 与 `--runtime`，`install_monitor.py` 的"手动执行"提示内嵌真实路径。
- `patch_install.client_running()` 用 `pgrep -x ZCode`，本机进程名可能是 `zcode-cli` 而漏检；它只决定走安全路径，无害，但**测试时不要靠它判断客户端是否在跑**。asar 被占用的收尾必须由宿主以外的监控进程执行，不能依赖 ZCode 自己的定时任务。
- 热/冷清单：`overlay.js`、`turn-stats.js` 热重载（主桥 mtime 监听：`hot_reload:true`=2s/缺省 5s/`false` 关）；`zusage.py` 常驻进程由 loader 按 mtime 自动重启；`inject-main.cjs` 是唯一冷文件（ipcMain/监听器注册与常驻泵都在它体内，只能随客户端完全重启生效）；六个子模块 `quota-client.cjs`、`model-puller.cjs`、`plugin-updater/release/storage.cjs`、`engine-patch.cjs` 自 v258 起由 loader 的 `hotReloadMainModules` 同拍热换（mtime 轮询→语法预检→dispose→清 require.cache→按依赖方向重建：quota 先落并联动重装 modelPuller 的 decryptValue 注入、release/storage 联动重建 updater 与 notes→`_hotLoadedAt` 销账→广播；updater 组 busy 在途顺延；watcher/定时器一次注册不得在热换路径重建）；`hot_reload:false` 时整链短路——mtime 轮询与更新链 `onRuntimeSynced` 两条路径都被入口门挡住，回退为待完全重启。**冷文件结论只在旧版 loader（未含热换循环）上成立**；新 loader 部署并重启一次后，上述六模块更新即零重启生效。
- **marker 热销账（v258）**：`ack_restart` 对启动后才写入的 marker 默认不动，唯一例外=loaded 顶层 `_hotLoadedAt`（键=文件名、值=热替换完成毫秒）覆盖全部 hash 条目且每条 `loaded[key]==digest` 且时间戳≥createdAt 且不含 `inject-main.cjs`（loader 自身只能随重启生效）→ 整单销账。`_hotLoadedAt` 是 loaded 顶层键，**绝不进 marker 的 `hashes`**（restart_notice 白名单会拒绝、`_hashes()` 会剥 `_` 前缀）；pending-install/installation 发布门控不受热时间戳影响。更新器 `syncInstalled` 落盘后先 `await options.onRuntimeSynced()`（宿主热换+销账）再算 `restartRequired`，红点零闪烁；旧主进程装配新包时无该回调，行为不变。
- 插件→运行目录同步有 hash 基线/mtime 热修保护（`preserved`）；根 `install.py` 的运行文件复制是直接覆盖，不能承诺同等保护。向运行目录覆盖任何文件前先 diff 运行目录与来源基（运行时可能领先所有工作树，直接 cp 曾静默降级）；并行会话活跃时 `sync_plugin.py` 会把他人未提交的根文件改动扫进副本与运行目录——浮层/更新器异常先排查这条路径。
- 热修纪律：叠加部署不整体覆盖；先备份 `.pre-<原因>-<时间戳>`；原子替换（tmp 同名过 `node --check` 再 mv）；判断运行目录实际版本用 diff 根文件 + stat mtime + 备份名，**不信 diag**（diag 约每 15 次拉取才落盘，滞后数分钟；`diag-0.json` 是非活跃窗口不能当泵健康探针）。运行目录分叉早于 main 时一步三方合并会回退已合入的改动，须两步（先演进到 main 再叠修复）。
- **部署后必须验证重注入，不能假定热重载已发生**（2026-11-07 实证）：热重载轮询跑在宿主进程侧，客户端窗口被遮挡/后台时轮询被 Chromium 后台节流（最长可到约 1 分钟一拍），`cp+mv` 原子替换可以无限期不触发重注入——曾实证连续 3 次部署约 20 分钟后用户端仍跑旧代际（用户看到的是初次注入的旧 UI，其间所有部署全部未生效）。重注入的判定依据是「代际重建事件」而非 diag 内容：`diag-0.json` 的 `FATAL.*` 计数字段（如 `rotPrevTick`）随重注入整体重建而归零/消失——`touch` 运行目录热文件后等 ≤70 秒（覆盖后台节流最长周期），字段归零即重注入铁证；字段值不变就是没重注入，可重复 touch 强制触发。与上条「不信 diag」不矛盾：diag 内容滞后不能判断文件版本/泵健康，但「计数字段归零」这一事件只在新代际首帧发生。未拿到归零证据前，交付措辞保持「已部署、待重注入验证」，不写「热重载已生效」；用户反馈「改动没生效」时先查这条再查代码。

## 3. 配置与开关

- 配置只合并需要的键，不整体覆盖 `config.json`；保留未知键、用户显式关闭与个人路径。插件配置事务在锁内重读、合并，再同目录原子替换；损坏或非对象配置不能被默默重建。`config.example.json` 是模板，不可原样执行占位路径。
- 缺字段默认值、非布尔异常值与显式 `false` 不能混为一谈。自动安装恒开（v172 移除 `plugin_auto_install_overlay`/`ZUSAGE_PLUGIN_AUTO_INSTALL`，遗留值只保留不消费），仅 `.plugin-overlay-optout` 能豁免。`plugin_auto_update` 独立；损坏或非布尔更新配置不启动自动更新。`restart_notice`（issue #139 起）自 v172 改为控制 ⚙ 齿轮红点（主进程推送 `restartNotice` 布尔，overlay 消费）：显式 `false` 才关红点，缺省/损坏/非布尔保持开启；不再门控任何文字输出。
- 主桥 `readCfg()` 的 `python_path` 缺省与空值归一为平台默认（win32=`python`，其它=`python3`），三个 spawn 点直接读它。

## 4. hooks 契约

- `hooks.json` 是 command+shell 回退链 `python3 → python → py -3`（POSIX sh 与 Windows `%ComSpec%` 都支持 `||`，宿主丢弃成功 hook 的 stderr）；`.mcp.json` 以 `command: "node"` 启动 `mcp-launch.cjs` 透传 `usage_mcp.py`（stdio MCP 按 `shell:false` 经 cross-spawn 直接 spawn、单命令无回退，Windows 无 `python3`、macOS CLT 无 `python`；宿主给 MCP 子进程 PATH 末尾追加 Electron Node fallback shim——`ZCODE_NODE_FALLBACK_EXEC_PATH` + `node`/`node.cmd` shim，未装 Node 也能解析 `node`，shim 准备失败时降级回原样 ENOENT）。python.org 安装器从不建 `python3.exe`；Store 桩是 PATH 真实文件、存在性检查全过，只有执行能区分（退出码 49、广告走 stderr）——launcher 探测按 `--version` 退出码 0 且 stdout 匹配 `^Python 3\.\d` 双重校验（Python 2 残留一并排除），全部候选失败时 stderr 诊断 + exit 127。
- SessionStart `matcher` 必须 `startup|resume`（引擎只派发这两种；桌面重启=恢复原会话 `source=resume`）。`timeoutMs=60000` 不得收紧：asar 重打包是磁盘密集操作，中断可经 pending 标记恢复。
- SessionStart 输出：`systemMessage`/`suppressOutput` 引擎无消费者，用户可见提示必须走 `additionalContext`（`_nudge`/自检失败分支双键同写是有意设计；v172 起正常安装/待重启路径不再输出，仅剩故障提示）。hook 在远端会话（SSH/WSL 时在远端主机执行、无 asar）必须静默 no-op；拿不到交互 sudo 只能报告不硬试。
- 自然触发证据：`__pycache__/*.pyc` 是安装期编译产物不算执行证据；可靠证据=运行目录被创建/更新 + `plugin-session-start.json` 的 source/pluginRoot/result。手动执行 hook 不等于自然事件验收。
- 引擎已核实事实：命令名=文件名、无 `/插件名:` 前缀；`allowed-tools`/`model` 字段只解析展示无运行时效果；`${user_config.*}` 仅注入 MCP 声明；MCP 工具全名 `mcp__plugin_<插件名>_<服务键>__<工具名>`；插件体系无 Uninstall hook（注入孤儿靠 `/uninstall-overlay` 兜底）。Python→Node 全量迁移已评估并否决（hooks 无 env 字段、锁无 Node 等价物、远端链必须留 Python），勿重启整轮调研。

## 5. sudo 与卸载

- sudo 提示必须保留目标用户 HOME/PATH 与用户产物归属：node 候选顺序 PATH → `SUDO_USER` 的 `~/.nvm/versions/node/*/bin/node` 按版本降序 → 系统位置；装完归还运行目录归属。remove 目标只读时先只读判定，确无注入则写豁免标记免 root 放行；提示按部署形态与操作区分。
- 卸载只移除本项目注入，不用旧 asar 备份回滚客户端版本；未注入时移除可成功，但读不到目标不能假装已卸载。GUI 卸载只清组件注销 + 缓存副本 + installed_plugins 条目，**不碰** asar 注入行/运行目录/市场注册（known_marketplaces + marketplaces 克隆）；彻底卸载顺序=`/uninstall-overlay` + 重启 → GUI 卸载 → 移除市场与克隆 → 删运行目录。`.plugin-overlay-optout` 阻止自动安装重注入与全部提示（v172 起无「安装提醒」类目，optout 是唯一静默出口），但不关闭运行文件同步/插件更新。
- 自动安装/修复可能受权限、事件触发、宿主结构影响，成功后仍需重启；不替用户重启，不用强制提权掩盖失败。

## 6. 更新器与渠道

- 更新渠道由 `readChannel` 按注册来源**和市场缓存清单**共同判定：清单为 zip 源的 GitHub/GitCode 来源是 Release 渠道（ZIP、manifest、版本一致，安装后 `verifyCommittedRelease` 复核宿主安装记录）；清单为源码路径的仓库来源判为 `market` 渠道，与本地目录来源同链，由宿主插件管理器按清单直接更新。源码清单的 `source` 是**相对路径字符串**（`"./plugins/..."`）不是对象，判定必须识别字符串形态；`readChannel` 读的是市场缓存清单而非注册来源，刚切源缓存未刷新会暂判旧渠道。安装前校验门 `validateCatalog` 已按维护者决定移除，不要加回。不静默切换用户市场来源，不启用被禁用插件。
- GitHub Release 渠道的 API 检查失败（限流/不可达；「无正式版，不能安装开发分支」与分页上限是渠道健康信号，**不**兜底）自动退回注册 ref 的渠道清单：`githubReleaseFromCatalog` 与 GitCode 渠道同构，渠道身份不变，清单 sha256（`catalogSha256`）与下载 manifest 交叉比对。清单兜底意图的安装复核有三处同构实现（`plugin-updater.cjs` 的 `verifyCommittedRelease`、`verifyRuntimeSync`、`overlay_install.py` 内嵌 `migrate` 回退）——新增意图形状必须三处同改且 migrate 侧要带 `typeof` 守卫（运行目录 release 模块可能过旧）。**例外：仓库改名迁移意图与 GitHub 渠道镜像回退意图（`mirror:true` 行，specs/github-mirror-fallback.md）刻意不改 `migrate`——能写出这两种意图的 updater 必然导出可复核它们的 `verifyRuntimeSync`，migrate 永远见不到；改名例外理由另见下文「GitHub 仓库改名迁移」条目的「不改的两处」子条目。**
- `PLUGIN_ID` 写死 `zcode-token-usage-statusbar@zusage-marketplace`，同名市场恰好一条记录（注册两个同名来源直接报错）。无 alpha/预发布通道：STABLE 正则 + prerelease 硬拒（`release_tool` 断言 prerelease 为 false），`compareVersions` 支持 pre 段但候选过滤不放行。
- 手动检查在 `busy=true` 后、取锁前立即 publish `checking`；撞锁抛"另一个更新进程仍在运行"；auto/定时 tick 路径保持静默不闪 checking。立即更新卡有 downloading 阶段与下载/安装双进度条，缺 progress 的旧主进程自动隐藏。
- 发版后 raw.githubusercontent 按分支名有约 5 分钟 CDN 缓存：Release 渠道清单滞后=下载 zip → 按旧清单装 → 版本未前进 → 报"插件管理器未提交新版安装记录"并按短间隔重试重下；market 渠道切源缓存未刷新=一次"更新期间市场来源已变化"后自愈。诊断更新失败先对时间窗。
- 更新日志（v202）：`plugin-release.cjs` 的 `fetchBytes` 第 4 参 `allowedHosts`——日志拉取经 `notesFetch` 只放行 `api.github.com`/`api.gitcode.com`（`NOTES_API_HOSTS`），与资产下载白名单（`DOWNLOAD_HOSTS`，由 `RELEASE_HOSTS` 展开）分开维护，放宽任一须连同测试；日志走 `release-notes`/`release-notes-list` 两个插件请求动作，flavor/repository 一律由主进程 `readChannel` 决定（渲染进程只传 version/force，market/local 渠道回 unsupported-channel 不联网）；缓存 `plugin-notes-cache.json` 落运行目录（TTL 1h、24 条上限、损坏按空重建），非发布素材不进分发链；安装失败目标持久化为 `plugin-update.json` 的 `lastFailure`（成功即清，当前版本追上亦清）；`lastError`（v278）记录最近一次检查/安装失败的错误消息——检查阶段失败此前完全不落盘，浮层不在时它是唯一痕迹（成功即清，取消类不写，500 字截断，损坏丢弃；恢复路径 syncInstalled 成功一并清除）。GitCode 匿名 release API（v5、`direction=desc`、`published_at` 恒空用 `created_at`）2026-11-01 实测可用。
- GitCode 双渠道校验（`plugin-release.cjs` 的 flavor 分支、`sameAssetUrl` 主机模式、`fetchBytes` 白名单）必须一起改并有测试锁定；gitcode flavor 的 `validateManifest` 放松 `manifest.repository`（上游而非镜像）；清单不一致 gitcode 直接报错。模拟渠道链路的测试不能用插件 `fetchBytes` 拉 raw.githubusercontent（白名单不含，真实链路由宿主 CLI 拉）。
- **GitHub 仓库改名迁移（探测式，预埋于更新器）**：宿主 `known_marketplaces.json` 里的注册来源烙的是用户 add 时的仓库名且宿主刷新永不改写（2026-11-09 读 ZCode 3.17.2 引擎 bundle：刷新单个市场的函数把传入的 `source` 原样写入注册记录；zip 下载器手动跟随重定向，最多 5 次，超限报 `Plugin zip download exceeded redirect limit`。混淆符号名随版本轮换，复核用 `LC_ALL=C grep -a -F` 搜这几个各只命中一处的字面量：`source:e.source,name:o.manifest.name`、`Plugin zip download exceeded redirect limit`、`dia=5,`、`known_marketplaces.json`）；改名后 GitHub API 响应体里的资产 URL 被规范化为新名（2026-11-09 以已转移仓库 spf13/hugo→gohugoio/hugo 实测：旧名 API 先 301 到 `/repositories/<id>/…`，`browser_download_url` 已是新名；`github.com/旧名` 返回 `301 Location: 新名`），于是 `validateRelease` 资产比对与 `githubReleaseFromCatalog` 清单比对按注册旧名全挂。宿主侧不受影响：旧名注册的 zipball 市场刷新照常（API 301 → `/repositories/<id>/zipball` → 302 codeload）。迁移设计：
  - **唯一信任锚是 GitHub 官方答复，两个独立来源**：`probeRepositoryRename` ①优先 `GET api.github.com/repos/{名}`（旧名先 301 到 `/repositories/<id>`，再返回当前 `full_name`，经 `fetchBytes`，下载白名单收窄为 `api.github.com` 单一主机，重定向到资产域/GitCode 域一律拒绝，且响应必须是自洽的仓库对象：整数 `id`、`owner.login/name` 与 `full_name` 一致，否则按 API 失败处理）；API 给出合法仓库名即为定论（同名=未改名，不再用网页推翻）；②API 失败（限流/不可达/404/非法名）才落到 `HEAD github.com/{名}`：Location 必须 https + github.com 同主机、合法 `owner/repo` 且 ≠ 原名（大小写不敏感）。API 优先的原因是本机实测（2026-11-09，Clash fake-ip）`github.com` 网页主机对 curl 与 Node 都会连续 504/超时（项目既有的 release 资产下载路径同样受影响），而 `api.github.com` 每次都通，且目标用户群正是代理环境；网页来源的价值是不占 API 匿名配额。任何失败一律 null，探测无果必须原样抛错，绝不静默换源；测试必须同时注入 head 与 lookup（第二、三参，默认实现会真实联网），updater 侧经 `options.probeRename` 注入。**默认回归不得联网**：调用方注入了 `fetchRelease`（接管网络层）而未注入 `probeRename` 时探测默认关闭；旧 release 模块无 `probeRepositoryRename` 导出（新旧模块版本错配）时同样返回 null。验证法：用包装 `https.request/get` 的网络陷阱（`NODE_OPTIONS=--require` 登记 GitHub/GitCode 主机请求）跑全量 Node 与 Python 回归，应为零条——这条曾在首版实现里漏过一次真实请求。
  - **触发点**：仅 github flavor 的 Release 渠道，且仅当 API 检查与清单兜底都失败、失败又是**来源/仓库不一致类校验错误**时才探测——`RENAME_SUSPECT` 匹配「GitHub Release 资产来源或大小无效」（API 响应体资产 URL 被规范化为新名）或「GitHub 渠道清单下载源与注册仓库或版本不一致」（清单新名 vs 注册旧名；限流时兜底到清单后同样落到这里）。超时、限流、宿主 CLI 刷新失败等纯网络类失败与健康信号（「不能安装开发分支」/「安全分页上限」）一律不探测：它们在受限网络（目标用户群含大量国内代理环境）里本就慢，探测只会把失败的检查再拖长，且此时拿不到改名证据。文案变动须与 `plugin-release.cjs` 的两处 throw 同步，改名用例走真实校验函数，失配会变红。「资产来源或大小无效」同一条文案也会在资产状态非 `uploaded`、体积越界时抛出，这类非改名失败每次检查多一次探测：仓库未改名时 API 腿是 1 次请求（直接 200，答复同名即定论），真改名时是 301 + 200 共 2 次（各占 1 个匿名配额单位）；API 不可用再多一次网页 HEAD。受限且 fail-safe：API 与网页腿都不响应时实测约 38 秒（API 腿 30 秒空闲超时 + 网页腿 8 秒 socket 超时）、理论上限约 70 秒（`fetchBytes` 60 秒总时限 + 10 秒守卫），发生在 `check()` 持更新锁的异步段，不阻塞 UI 与会话启动（自动更新由 SessionStart 以分离进程拉起）。探测对象是仓库**当前所在名**——已有迁移记录取记录里的 `to`，否则取注册名——所以再次改名天然可追；探测是尽力而为，探测抛错不得掩盖原始错误；命中后按新名整体重查，**重查成功才更新** `state.repoMigration`（随本轮 `save()` 落盘，未经证实的目标不持久化），重查失败的错误带「仓库已改名为 X，按新名重新检查仍失败：…」上下文；探测结果等于注册名视为改回，清除记录。
  - **记录**：`plugin-update.json` 的 `repoMigration: {from, to, at}`，`from` 恒为注册名；`readState` 与 `save()` 的显式字段清单都必须带它（漏任一处会在进程重启后静默丢记录）。有记录时 `migrationRepoFor` 直接用 `to`，后续检查零额外请求；注册来源变化（`from` 不再匹配）豁免自然失效。记录与 `plugin-update.json` 同信任级别（本地可写），不会自动回退：`to` 消失而注册名恢复时需人工解除——**只有删除 `repoMigration` 键有效**（重新注册同一来源无效，因为 `from` 仍等于注册名；把来源改注册为另一个仓库名则记录自然失效）。这是有意取舍——粘滞记录同时让已迁移用户不受旧 owner 名被抢注的影响。
  - **意图与复核**：`pendingRelease.channel.repository` 存迁移后新名（与 `release.repository` 自洽），`source`/`kind` 保留注册原值。豁免只在存在迁移记录时生效：`channelMatchesRegistration` 先走原整体深比较，不通过才用 `sameChannel(…, migration)`；`repositoryMatches` 要求 from/to 均为合法 GitHub 仓库且与注册名/意图名一致（大小写不敏感），`kind`/`source` 恒严格。GitCode 注册来源一律不豁免：`verifyCommittedRelease` 的渠道形态取自宿主注册来源（`currentChannel.flavor || channelFlavor(currentChannel)`），而不是持久化意图里的 `flavor`——后者在本地可写的状态文件里可被篡改（`tests/plugin-release-updater.test.cjs` 的 forged github flavor 用例守护）；check/install 路径里 `selectedChannel` 恒等于注册来源，对 GitCode 天然不可达。消费方：`installUpdate`、`verifyCommittedRelease`（第四参）、`verifyRuntimeSync`（读 pending 的 `repoMigration`）。非迁移路径语义与改动前一致，仅 `plugin-update.json` 多一个 `repoMigration: null` 键。
  - **不改的两处（审查结论）**：①`overlay_install.py` 内嵌 `migrate` 是冻结的旧版适配器——仅当运行目录 updater 不导出 `verifyRuntimeSync` 才启用，而迁移记录只会由新 updater 写入，其验收走 updater 自带验证器，适配器永远见不到迁移意图；改动它只会影响旧运行目录的升级路径（曾因调用旧 release 模块不存在的导出而回归、且守卫顺序引入 TypeError），故保持零改动。`tests/test_runtime_sync_guard.py` 的 `test_migrate_fallback_is_frozen_for_git_source_on_stale_release_module` 与 `test_migrate_fallback_reports_missing_channel_as_invalid_intent` 只守护两类已知回归（对旧 release 模块不存在的导出的调用、缺 `channel` 时的 TypeError），并不锁定适配器的语义——放宽其比对的改动仍须评审把关；这与上面「三处同构」纪律不冲突：将来新增的意图形状照样三处同改，只是仓库改名迁移意图本身不需要。②`validateManifest`/`downloadRelease` 的仓库校验保持严格：渠道清单与同次发布的包 manifest 出自同一次 `release_tool publish`，改名前构建的包（manifest 的 `repository` 取自构建时的 `--repo`，是旧名）在新名渠道下会依次被 `release_tool.py verify`（`--repo` 与 manifest 不一致即报 `repository disagrees`，发布时就拒绝）、更新器 `validateManifest` 与 `installUpdate` 的清单新鲜度门拦下，放宽它既不可达又会在 `verifyCommittedRelease` 留下「版本已前进、运行目录未同步」的半成品风险。
  - **新旧版本兼容（2026-11-09 实测）**：旧版写出的状态（无 `repoMigration` 键）与新版写出的普通状态，新旧 `verifyRuntimeSync` 互读都通过；旧验收器会拒绝新版写出的**迁移意图**（失败即关闭），但写入者与验收者是运行目录里同一个 updater 文件，正常流程不会出现「新写旧验」。更新器与发布模块版本错配（同步写文件的窗口期，或某文件被热修保护 `preserved`）双向——新 updater+旧 release、旧 updater+新 release——跑完整更新器集成测试全过。老用户首次升到含该能力的版本全程由旧 updater 完成，意图与复核语义同旧。
  - **探测答复的信任等级（残余风险，有意接受）**：探测答复决定更新器去哪个仓库命名空间取包——这是本特性**新增**的信任依赖，不能说成与改名前等价。仅在按新名重查成功后才持久化。安装前**只有一道**拦截：`installUpdate` 在 `prepareRelease`（下载并解包校验）与 `refreshMarketplace` 之后、`cli install` 之前，要求宿主刚刷新的注册 ref 清单点名新仓库（`githubReleaseFromCatalog(catalog, selectedRelease.repository)`）。`verifyCommittedRelease` 的 sha256 复核发生在宿主提交**之后**，只阻止运行目录同步与待同步意图清零，拦不住宿主已装入的包。这道门并不独立于探测：GitHub 来源的宿主刷新首跳同样是 `api.github.com`，有效 TLS 下控制该主机的中间人可以同时满足探测与清单两个前提；在清单兜底路由（`checkedVia=release-catalog`）里 `selectedRelease` 取自检查阶段读到的清单，此门虽在 `refreshMarketplace()` 之后重新读取，但两次读取同源，在该路由下不提供独立约束。残余风险面因此是「有效 TLS 下控制 `api.github.com` 应答」的攻击者（如受信任的 SSL 检查代理）：若其同时控制 `github.com` 的下载内容（这类代理通常如此），改名前就能对注册名发动等价的伪造，新增的是「命名空间由远端答复决定」这一依赖。伪造探测的可观察后果是记录粘滞、此后每轮检查都先下载并解包校验攻击者仓库的包（≤16 MiB）再被新鲜度门拦下。**可选强化（未采用，需维护者决策）**：接受迁移时要求新旧 owner 一致（大小写不敏感），使攻击者必须控制同一 owner 命名空间；代价是将来若连同 owner 一起转移，迁移会静默失效，只能走手动切换同名市场来源。
  - **边界与维护纪律**：market/local/gitcode 渠道不走迁移；改名前发布的旧版插件（无探测代码）改名后只能手动按用户指南切换同名市场来源。**只改仓库名，不改 owner**：同一 owner 下旧名命名空间仍归 owner 所有，第三方无法在旧名建仓；若 owner **账号本身**改名或被删除（仅把仓库转移给别的 owner 不会释放旧 owner 名；这是 GitHub 平台行为，依据其官方文档，本仓库代码无法核对），旧 owner 名可被他人注册，注册后旧名下的 releases/清单即抢注者的内容，而更新器的旧名路径按注册名信任其服务内容（既有行为，探测不会介入，因为旧名检查会成功）。**改名后不得在旧名下新建同名仓库**（会同时破坏重定向）。改名后立即发布下一版，使清单与包 manifest 都烙新名。完整步骤见 [docs/maintaining.md](../../docs/maintaining.md#仓库改名)。
- 配置/更新/安装锁跨 Python 与 Node；OS advisory 锁文件永久保留，不通过删锁文件解锁。更新租约/所有者与旧锁恢复是另一层协议，不把冲突当成功，也不删运行目录绕过并发或热修保护。

## 7. 打包与发布

- 本地同步 ≠ 打包 ≠ 校验 ≠ 发布预演 ≠ 提交/tag/Release/渠道推送；源码改版、正式渠道发布、用户安装副本升级是不同步骤。
- 两份 `plugin.json` 与根 `marketplace.json` 的插件身份/版本须一致；正式渠道清单是生成的 `marketplace-release.json`，不要覆盖源码市场入口。`release_tool.py build` 的输出目录须尚不存在，包只含枚举分发文件；`verify` 校验身份、文件集、SHA256 与安全解包。
- `publish --dry-run` 不是离线检查：仍有 GitHub 只读 preflight，要求已提交源码、本地/远端 tag 与目标提交一致、Release 不存在及非空 UTF-8 更新说明；预演不授予发布权限。`publish --gitcode-repo`（需 `GITCODE_TOKEN`）在 GitHub 发布验收后生成 `plugin-releases-gitcode` 清单与同 tag 资产，镜像上须先有同一个 tag 且指向发布提交（创建 Release 的请求不带 `target_commitish`，见发布技能的 GitCode tag 闸门）；GitCode 段认证未配置时该段失败属预期，不代表 GitHub 段失败。
- 覆盖/删除已有 Release 需用户明确指令，删除前 `gh release view --json body,assets` 存快照。`--publish`/`--confirm` 是工具安全门不是授权替代；提交、推送、tag、Release、渠道写入按当前明确授权执行。
- 配置、数据库、诊断、本地热修不是发布素材；可信同步保护用户改动，解包保留路径穿越、链接、重复项与文件集限制。本地统计只读数据库不上传；远端查询用配置/宿主连接通道、插件更新联网下载代码，不能笼统宣称"不联网"。
