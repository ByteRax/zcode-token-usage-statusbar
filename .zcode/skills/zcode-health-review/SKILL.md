# 项目健康巡检

发现值得处理的问题，而不是制造改动。允许零发现；不以文件长度、问题数量、测试总耗时或使用某种架构模式给项目打健康分。职责与验收契约见 [spec](../../../specs/project-health-review.md)。

## 1. 确定本轮范围与授权

先读根 [AGENTS.md](../../../AGENTS.md)，按其索引读取本轮涉及的域规则。以当前检出为准，不混用其它工作树、生成副本、已安装宿主或正式发布版。

扫描深度与动作权限分别确定，不能由「全面」「深度」「优化」等单个词推导修改授权：

| 扫描深度 | 范围 |
| --- | --- |
| 日常巡检，未指定时默认 | 可信基线后的变更及上下游，加风险抽样；轮换复查较久未覆盖的领域 |
| 专项检查 | 用户指定领域及必要依赖，不顺带全仓重构 |
| 全面体检 | 对检查目录各域先做只读盘点，再按风险深入；说明未覆盖部分 |

| 用户意图 | 动作 |
| --- | --- |
| 扫描、检查、找优化点 | 只读取证和报告；不写源码、spec、台账，不同步或部署 |
| 为问题出优化方案 | 复核并筛选问题，转入方案技能的只读分支 |
| 明确要求巡检并修复／实施优化 | 完成问题清单后，转入方案技能的实现分支；不重复询问已授权且明确的事项 |
| 要求保存报告／维护台账 | 仅授权指定报告或台账写入，不因此获得代码修改权限 |

遵循当前会话实际模式与权限。读取历史报告或另一个 skill 不会扩权；用户已有明确禁止或更窄范围始终保留。请求确实含糊时，先做安全的只读定位，再只问影响结果的必要问题。

## 2. 建立可复核基线

- 记录仓库／检出位置、分支或 detached 状态、HEAD、相关 staged／unstaged 差异及未跟踪文件。检查已有修改与生成物差异；不读取或输出凭据、个人数据库、原始敏感日志。
- 用户提供或明确指定的历史巡检记录可用作线索；需要历史复查、台账或问题交接时，读 [问题与基线契约](references/findings-workflow.md)。没有可访问记录就说明本轮是新基线，不搜遍用户目录找历史，不默认写持久化文件。
- 核实历史 HEAD 可比较、相关路径仍存在，差异包含未提交内容；HEAD 相同不代表没有变化。基线失效时重新取证，不把首次发现称为新增退化。
- 对高风险疑点先运行必要的隔离定向检查。检查脚本是否会联网、查询真实账号、启动客户端或写安装目录；默认不运行真实模型／认证 smoke，不解密凭据验证供应商。
- 测试期间冻结自己的被测文件编辑。前后复查目标文件状态；若有并行变化，重测受影响项或标为不可复核，不将该结果更新为可信覆盖。不能仅凭工作区脏就断定他人正在写，也不能忽略已确认的并行写入。

## 3. 选择检查点并收集证据

读取 [项目检查目录](references/check-catalog.md)，只展开本轮相关领域。首次日常巡检先建立模块概览和风险抽样，不以「没有旧基线」自动执行全量测试。日常检查除变更链外，补查近期记录暴露的隔离／分发等高风险边界；没有覆盖记录时，说明抽样依据。全面体检覆盖目录，不等于每个测试或安装脚本都要执行。

沿「输入 → 状态所有者 → 生产者／传输 → 消费者 → 失败与清理」追踪。结合源码、契约测试和必要运行证据；静态阅读不能替代 UI 行为或实际热更验收。测试、规则、注释不一致时先说明冲突，不能只为匹配现状而改规则或测试。

先完成选定范围的最低限度只读盘点，再决定修复；不扫描到一处就开始修改。复杂且互不依赖的读取可按当前宿主和用户子代理策略分工，返回可复核位置；不硬编码代理数、角色参数或工具能力，最终判断由主会话承担。

每个发现至少给出：

- 触发条件、受影响链路及实际影响；源码位置／符号和相关测试或运行证据。
- 已确认的事实、待验证的假设和证据缺口，不能混写为确定缺陷。
- 违反的现有契约或可测量收益；最小处理方向与保留现状的代价。

问题是否成立与修复是否通过验证分开判断：可达逻辑和明确契约已足以证明缺陷时，可标已确认并建议修复，同时注明尚未运行测试或影响范围待核实。不要仅因缺少运行记录把正确性缺陷降成风格优化，也不要把「问题已确认」写成「修复已验证」。

不能只凭文件大、少量重复、裸切片或可选导入就认定缺陷。分片、依赖闭包、缓存、跨端展示等先核查有意设计和兼容范围；对不存在的模块标为不适用，不从历史或其它工作树恢复。

### 对抗审查：巡检阶段

完成只读盘点后、交付或交接清单前，按 [对抗审查方法](references/adversarial-review.md) 反证候选发现及高风险漏检：核对契约、触发条件、基线、实际影响和已有决定，主会话核实审查结论。按风险选择范围；独立审查可用且符合当前授权时优先使用，否则执行主会话反证并标明非独立。只读权限不因审查发现缺陷而扩大；无发现或有意设计可如实结案，尚缺证据则标待验证。

## 4. 去重、决策与交接

用模块、契约和根因匹配历史问题，不单靠标题或行号。归为新增、持续存在、已消除、重新出现或待复核；历史已验证问题重新出现需有前后证据，无法证明时只报告当前发现。

处理建议分三类：

- **必须修复**：已证实的安全／隔离、正确性、运行中断、分发或兼容缺陷；优先级不等于修改授权。
- **值得优化**：有可验证收益、风险可控的可靠性或维护性改进。
- **仅记录**：证据不足、收益不明、超出范围或需要用户决策。接受风险仅记录用户已有决定，不替用户接受安全风险。

同根因问题合并，保留不同触发场景；标记依赖和共享文件，先解决基础契约。先前暂缓或接受风险的条件未变时不反复催改；条件变化时解释重新评估的原因。

仅巡检到此输出结论；需要方案或实现时，携带 [交接包](references/findings-workflow.md) 进入 [zcode-prd-to-spec](../zcode-prd-to-spec/SKILL.md)。交接是当前任务内的职责切换，不自动创建／发送其他会话，不反复在两个技能之间重新扫描。若目标技能不可用，报告缺失，可在现有权限内给方案；缺少安全实现规则时不猜测执行。

## 5. 交付与后续复查

报告以本轮实际证据为准，保持精简：

1. **范围与基线**：扫描深度、比较依据、已检查和未覆盖领域。
2. **问题清单**：编号、分类、证据／影响、处理建议、历史变化；无值得处理的问题时直接说明。
3. **检查结果**：真实执行的命令、结果、失败和跳过原因；注明哪些只是静态判断、哪些已做行为验证。
4. **对抗审查与下一步**：交代审查范围、独立性、发现的处置和未覆盖项；给出处理顺序或尚缺证据，不因发现问题自动改码。

只在明确授权保存时按问题契约更新指定台账，并回读核对。保存历史不授予未来写权限；不自动提交、上传、发布、部署或创建周期自动化。用户要求实施后，由方案技能分别返回代码、测试、副本、部署和运行验收状态，不能用「已写代码」关闭仍待验证的问题。
