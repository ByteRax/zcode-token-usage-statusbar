# 更新日志交付：版本身份、来源与验收

在起草说明、发布前检查、发布后验收和修订正文时读取本文件。它约束发布侧如何为「插件更新 > 更新日志」提供可信内容，不授权开发或部署客户端功能，不改变 SKILL.md 的 B–F 授权边界。

## 1. 先确认消费者是否已经实现

在**本次目标提交**中检查 `plugin-release.cjs`、`plugin-updater.cjs`、`inject-main.cjs`、`overlay.js` 及对应测试，追踪日志的获取、版本选择、IPC、缓存和展示。记录实际支持的来源、字段与文件路径，不从设计稿推断功能已上线。

- 尚未实现日志消费者：仍生成并验收对应版本的 Release 正文，报告「发布正文已就绪，插件内日志展示未实现」，不声称小红点后的日志入口已可用，也不把未实现的界面当作旧版发布阻塞。
- 已实现消费者：按实际合同准备资料，并完成第 5 节适用检查。缺必要资料、版本错配或已有日志功能回归属于发布前阻塞；单纯外部服务暂时不可达须记录未验证，不能伪报通过。
- 客户端应对旧版/第三方空日志或网络失败正常降级；这不免除维护者为本次新版本提供非空、准确正文的发布责任。

## 2. 固定版本身份与单一内容来源

在发布工作记录中保存：目标仓库/渠道、三段版本、tag、tag 剥离后的提交 SHA、上一正式 tag/比较基线、审核通过的正文文件及其 SHA256。阶段 A 尚无 tag 时先记录候选提交，阶段 B 提交/打 tag 后补核实最终 SHA；不要为收集日志身份提前创建 tag。以 API 的实际发布时间/修订时间为准，不把构建时间或当前时间伪装成发布时间。

- 同一正文输入用于预演、GitHub 发布与已授权的 GitCode 镜像，不独立手写多份不同内容。已存在版本化日志时优先复用或按现有流程导出；不要再引入第二套手工维护正文。
- 日志必须属于目标版本，禁止读取 `latest` 替代指定 tag。排除 draft、prerelease 和截图托管 Release；历史记录按实际版本规则与分页处理，不以 API 首屏或字符串排序宣称完整。
- 源码渠道的 manifest 版本号相同，不足以证明内容等同 Release。只有提交身份或现有可验证发布映射匹配时，才能把 Release 正文称为本次源码更新日志；否则标注参考说明或无匹配日志。
- GitCode 镜像使用同一 ZIP 时，manifest 中的 GitHub repository 与实际镜像来源是不同身份，保留既有合同。不要为了日志匹配改写 manifest.repository、ZIP/hash 或用户渠道。
- 仓库/渠道/提交映射记录优先放现有发布输出或证据文件；不要要求在提交内写入该提交自身 SHA，造成自引用循环。未实现的字段或索引不能仅通过改技能当成既有合同。

| 安装来源 | 发布侧提供与核对 | 不具备条件时 |
|---|---|---|
| GitHub Release | 指定仓库/tag 的正式正文、发布页、tag commit 与资产 | 报告正文未就绪或来源未验证，不替换为 latest |
| GitCode Release | 对应镜像 tag/commit、正文与相同资产；逐渠道回读 | 标明镜像日志未就绪，不自动切 GitHub 下载来源 |
| GitHub/GitCode 源码市场 | 目标源码快照内已有日志，或经验证的源码—发布映射 | 明确暂无匹配发布日志，同号 Release 只能作标注的参考 |
| 本地目录 | 当前源码中实际存在、与该版本关联的日志 | 缺日志正常降级，不因进入设置新增隐式联网 |

## 3. 面向插件卡片编写正文

按 `release-notes.md` 的模板维护一份正文：开头用 1–2 句概括用户价值；紧接需要重启、破坏性变化或迁移等关键升级注意，再写新增、修复与改进，测试/提交范围放后面。

- 每条说明包含可核实的变化、入口及必要条件。仅开发分支或 tag 之后的功能不进入本版正文。
- 保留完整限制，不为了卡片短预览删掉重要警告；不强制每次都有新增功能，没有就省略该章节。
- 使用标题、列表、普通文字、行内代码和明确的 HTTPS 链接。避免依赖 HTML、`details`、脚本、远程图片、复杂表格或只在 GitHub 可渲染的结构；不要求客户端执行正文里的命令。
- 仓库文件链接指向对应 tag/提交，不用 main 作为历史说明证据。外部链接允许查询所必需的非敏感参数，但不得包含 token、授权信息、本机路径或个人数据。
- 正文原文语言明确；如实际合同包含翻译或摘要，应从同一审核内容产生，保证重要限制一致，不临时调用客户端 AI 补全。没有翻译时不冒充已本地化。
- 若已有摘要/升级提示字段，检查其实际长度、转义与正文一致性；若没有，不为卡片自行发明 JSON schema、Markdown 标记或截取协议。

## 4. 打包、冻结与兼容

先核对 `release_tool.py`、`release_unpack.py`、两个插件 manifest 和已落地的日志消费者。当前 `--notes-file` 是外置发布正文，非第三个 Release 资产，不进入 ZIP；只有另行实现并验证的合同才能改变此规则。

- 不直接向 ZIP 塞入 `CHANGELOG.md` 或新增日志资产。不因日志 UI 需求擅自改 schemaVersion、文件白名单或更新校验。
- 如当前合同已支持随包日志，在 build 前完成对应内容和副本同步，并核对 `packageLayout.files`、打包白名单及实际部署读取位置。对非运行资料不机械加入冷文件/运行时名单。
- 包内日志/元数据变化属于包内容变化：重新同步、build、verify、历史解包器兼容验证及相关测试；提交后重建比对通过才能推 tag。已推送 tag 不移动，已发布资产不覆盖。
- 未发布阶段仅外置正文变化不需伪造新 ZIP，但须在阶段 C 前提具备时重新预演并固定正式发布使用的正文快照；仅预演且未获 B 授权时仍停在阶段 A。已发布正文修订按第 6 节执行，不运行会拒绝已有 Release 的 publish 预演。若正文从随包资料导出，确保两者同源且一致。
- 核对目标提交所有实际支持的旧版解包器/更新器路径；旧包缺日志字段须可降级。内容 hash 只能证明字节一致，不能当作独立签名。

## 5. 发布前与发布后验证

### 发布前（不触发真实安装或重启）

始终检查正文非空、非占位、版本/范围正确，关键升级注意可见，链接归属及敏感信息检查通过。

本次已授权 GitCode 镜像时，在阶段 D 前只读检查同 tag 是否已存在；若存在，先核对提交、正文与已有资产身份。正文不一致或资产存在冲突时先报告并处理授权范围，不启动会复用旧 Release 且上传资产的镜像步骤；检查失败不等于 Release 不存在。阶段 D 后仍须回读，防止中途变化。

日志消费者已实现时，使用现有隔离测试核验下列适用场景；记录实际执行的命令、结果和缺口，不虚构测试命令，不为发版临时扩大功能范围：

| 场景 | 必须验证的行为 |
|---|---|
| 有更新/已是最新 | 显示对应目标/当前身份日志，不被 latest 或历史选择串版 |
| 自动安装成功、待重启、重启后 | 保留真实安装目标日志；磁盘版本、运行状态不混同 |
| 安装失败/回滚/待重启时又有新版 | 不记录假成功，区分已安装目标与更高可用版本 |
| 源码/镜像/本地、同版本不同提交 | 来源隔离，无匹配身份时降级，不暗中切源或联网 |
| 断网、限流、空正文、缓存损坏 | 不阻断安装；缓存注明来源和时间，修订可重新获取 |
| 切换版本、并发请求、关闭设置、热重载 | 旧请求不覆盖新选择，无重复监听或销毁后更新 |
| 读取日志、历史不完整 | 不改变更新/重启事实，遵守原红点确认机制，不称历史完整 |
| 长正文、恶意 Markdown/URL | 限制大小、安全渲染，远程图片不自动加载，窄窗与主题可读 |

已承诺支持的行为测试失败时先修复/报告阻塞；不存在消费者时标记不适用。实机验收需使用真实 ZCode/Electron，独立浏览器截图不能替代；无宿主或未获真实安装/重启授权时标注未验证，不自动操作用户客户端。

### 发布后（只读回查，沿用现有授权）

1. 回读准确 tag 的 GitHub Release，核对正式状态、正文（仅归一 CRLF 与末尾空白）、tag commit、资产与审核快照。不能只检查 release name 或非空。
2. 已授权镜像时，通过项目现有 GitCode API 能力回读同 tag，单独核对正文和 tag commit，资产校验沿用发布工具。先读当前 `gitcode_mirror` 实现：若复用旧 Release 不校验/更新 body，必须补做只读比较，不能把上传资产成功视为日志同步成功。不要回显令牌或带凭据 URL。
3. 有正文差异或读取失败时，标明哪个渠道的日志未就绪，暂停推进该渠道清单；不删除重发 GitHub、不重传相同资产，也不擅自修改已有镜像正文。按正文修订授权处理，或报告阻塞；已经完成的其它渠道分别记录。
4. 对已授权推送的渠道，回读其远端清单和目标日志，分别记录包/清单可用性与日志可用性。CDN 滞后时有限重试或报告待同步，不改 tag/hash、不切来源。
5. 若消费者已实现，用真实下载资料或安全隔离环境核对对应版本展示。没有真实宿主则只报告发布资料验收通过，不能宣称用户界面、安装或重启已验证。

## 6. 修订与最终报告

只修订正文时，先存独立快照并确认准确仓库/tag，保留 tag/资产不变。GitHub 编辑不会自动同步 GitCode、包内说明或用户缓存：镜像正文写入须在用户授权范围内，否则列为待同步；包内历史资料保持不可变，可在下一版修正，不为文案重打同版包。

消费者已支持刷新时，以正常刷新/重试验证远端修订可见；无能力或无宿主时报告限制，不删除用户缓存制造成功，不把旧缓存误判为安装失败。

最终按来源分别报告：仓库/渠道、版本/tag/提交、正文来源与审核 hash、Release 正文验收、包/清单验收、插件内展示验收、未验证/不适用项。预演只报告准备情况，正式发布时间与 URL 等发布后才能确认。发布资料已就绪、渠道可更新、客户端已安装、界面已生效是四种不同结论。
