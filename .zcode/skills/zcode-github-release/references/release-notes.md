# 更新说明规范

目录：[核实范围](#核实范围) · [必写项](#必写项) · [正文模板](#正文模板) · [条目写法](#条目写法) · [风格](#风格) · [发布工具合同](#发布工具合同) · [修订已发布说明](#修订已发布说明)

同时执行 [更新日志交付](update-log-delivery.md)：先检查目标提交的日志消费者，再核对版本身份、来源、包合同与各渠道正文。客户端功能未实现时只交付 Release 正文，不把计划写成已上线能力。

## 核实范围

- 上界是本次目标 commit/tag，下界是上一正式 Release 的 tag：只选已发布、非 draft、非 prerelease 的 `vX.Y.Z`，排除 `screenshots-*` 等素材 tag，并确认它是目标提交的祖先（`git merge-base --is-ancestor PREV TARGET`）。
- 先取完整提交清单，再按 PR 归类。本项目先在发布分支打 tag、发布后才合并发布 PR，所以上一版自己的 PR 合并提交会出现在 `PREV..TARGET` 的首父线里，那不是本版内容，要过滤掉：

```bash
git log --no-merges --format='%h %s' PREV_TAG..TARGET        # 完整清单：每个真实提交
# PR 级索引：丢弃第二父已被 PREV 包含的合并（即上一版自己的 PR）
git log --first-parent --merges --format='%h %p %s' PREV_TAG..TARGET | while read -r m p1 p2 subject; do
  git merge-base --is-ancestor "$p2" PREV_TAG || echo "$m $subject"
done
gh pr view N --repo OWNER/REPO --json title,body,mergedAt    # 读 PR 正文（本仓库的 PR 描述写得很细，通常不必再读代码）
```

- PR 描述若带「发版说明素材」块（由 [zcode-review-fix-merge](../../zcode-review-fix-merge/SKILL.md#pr-描述发版说明素材) 约定），把它当作起点：条目可作为正文素材；重启要求与升级注意只在确有影响时并入相关条目，仍须对照 diff、测试和已提交文档核实，它只是作者自述。较早的 PR 没有这个块，照常读正文与 diff；块内的重启判定与 `pre-publish-checks.md` 命令结论不一致时，以命令为准。
- 直接提交到首父线、没有走 PR 的改动不在 PR 级索引里，以完整清单为准。上一版的发布 PR（分支名 `release/vPREV`）若带了 tag 之后追加的收尾提交，它的合并提交会留在索引里，但其中只有 tag 之后追加的提交属于本版。提交标题只是线索：用相关 diff、已提交文档和测试确认功能、默认值、支持平台和升级要求；不要写入未提交文件或 tag 之后的改动。合并提交、重复补丁、纯格式调整不逐条罗列。
- 没有上一正式版时在工作记录中注明「首个正式 Release」，选可核实的近期集成基线，在工作记录中注明 commit/比较链接；不要虚构上一版本或将全部仓库历史都说成本版新增，不以截图 tag 或开发分支版本号冒充已发布版本。
- 动笔前读一遍上一版正文，核对变化是否重复；章节按本规范，不沿用旧版冗长结构：`gh release view PREV_TAG --repo OWNER/REPO --json body --jq .body`。

## 必写项

先读 diff 核实以下影响；仅将本版必要提醒并入相关新功能或修复条目，不另设章节、不重复通用声明。测试结果与提交范围放工作记录或 PR，发布检查照常执行：

- **重启要求**：按 `pre-publish-checks.md`「重启要求」一节的 diff 命令判定。命中冷文件就在相关条目末尾用逗号或分号补「更新后请完全退出 ZCode 再打开」（涉托盘退出时注明从托盘退出）。
- **用户可见入口的删除、改名、默认值或配置键变化**（如状态条删一格、设置项或命令改名）：逐条写明，并指出替代入口。
- **升级路径限制**：已注册来源与渠道不同的用户如何升级、是否需要一次性迁移（切换到 `OWNER/REPO#plugin-releases` 或重装）。
- **能力成熟度**：额度适配器注册表（`quota-client.cjs` 里带 `unverified: true` 的条目，规则见 `.zcode/rules/quota.md`）以及 `AGENTS.md`、`.zcode/rules/*.md` 里写明未经实机验收的平台，相关条目用「尚未实机验证」等白话标注，不写成「已支持」；详细测试证据留在工作记录。
- 自动更新尚无一致渠道清单时，不写「自动升级已可用」。发布完成不等于客户端已安装；SHA256 是下载完整性校验，不是独立安全签名。

## 正文模板

对齐 ZCode 宿主官方更新日志结构，只保留以下两个章节（按此顺序，没有内容就整节省略）。直接从标题开始，不加摘要、日期头（齿轮悬停卡已渲染发布日期）、安装与升级注意、验证或提交范围。条数随本版真实改动体量自然呈现（热修可只有 1～3 条，常规版 4～10 条，大版本按独立改动逐条列出）；不凑数，也不为硬压条数把互不相关的改动塞进同一条。

```markdown
### 新功能
- 某入口或功能支持……，方便 / 可……
- 新增……设置，可指定……

### 修复与改进
- 修复……导致……的问题
- 某行为改为……，各处保持一致
- 收紧……的安全校验
```

## 条目写法

对齐 ZCode 官方更新日志的简洁白话体——用户在宿主与插件卡片里并排阅读两者的更新日志，粒度和语感保持一致：

- **单条凝练、一句一件事**：常规单条尽量控制在 **12～32 字**（含重启、迁移或限制说明时可适当放宽），一句说清「什么变了 + 带来什么结果或收益」。
- **句末不加句号**：列表条目末尾统一**不加中文句号「。」**（同一条内用逗号或分号衔接补充说明，结尾同样不加句号）。
- **不加粗前缀、不套八股模板**：不要写成 `- **状态条排序**：支持拖拽调整状态条顺序`，直接用自然动宾/主谓短句陈述。
- **「新功能」写法（自然多样，不死板每条都用「新增」开头）**：
  - 入口/能力 + 收益：`……支持……，快速 / 便于……`（如 `设置面板支持拖拽调整状态条各模块顺序，无需改动代码`）
  - 场景 + 结果：`……时自动……，不中断……` / `……后可一键……`（如 `自定义供应商页面支持一键拉取模型并自动检测可用性`）
  - 新增/内置 + 用途：`新增……设置，可指定……`（如 `新增系统状态监控，可在状态条查看 CPU、内存与磁盘占用`）
  - 仅在用户找不到入口时顺手点明位置（如「设置 → 维护」），不强行每条都列路径。
- **「修复与改进」写法（覆盖修复、优化与安全三类）**：
  - 问题修复（写用户看到的症状）：`修复……导致……` / `修复……的问题`
  - 体验优化与行为恢复（写变好后的结果）：`……改为……，各处保持一致`、`……更准确，减少……`、`……不再误报`
  - 安全与校验收紧：`收紧……的安全校验`、`……时严格校验……`
- **用词与排版细节**：
  - 界面按钮、菜单名或开关文案用中文直角引号「」（如 `「重启 ZCode」`、`「插件更新」`），不用反引号或粗体堆砌代码感。
  - 必要的产品名、命令或专有名词保留原文，中英文与数字间自然留一个半角空格（如 `修复 macOS 更新后状态条未自动恢复的问题`）。
  - 面向普通用户，不堆 tooltip、IPC、epoch、内部模块名、函数名、阈值公式、代际号（`vNNN`）、PR 号或提交哈希；也不要把技术细节塞进括号继续堆字。
  - 同一问题的多个提交合成一条；纯测试、重构、格式整理不单独写。
- **把必要提醒自然并入相关条目**：
  - 必须重启时，在相关条目末尾用逗号或分号补「更新后请完全退出 ZCode 再打开」；只影响部分用户时写明条件。
  - 迁移、入口删除、兼容限制或「尚未实机验证」同样并入相关条目，必要时附对应版本的操作指引链接。
  - 默认不解释 ZIP、manifest、校验文件或发布流程，不粘贴测试数量和完整提交清单。

本项目写法改写示例（仅示范表达，不能当成本版事实）：

- 「优化 quota epoch 竞态处理」→「修复切换账号后额度仍显示旧账号数据的问题」
- 「新增 tooltip 展示能力」→「鼠标移到速度数字上即可查看详细统计」
- 「加固 release_unpack 路径校验」→「收紧更新包解包时的路径与文件校验」
- 「热换主进程模块 + 重启」→「模型拉取支持自动探测路径与档位，更新后请完全退出 ZCode 再打开」

## 风格

- 默认简体中文；保留命令、设置字段、产品名和资产名称的原文，中英文之间留半角空格。面向用户解释变化，不堆砌内部编号、merge commit、格式清理和全部提交标题。
- 不使用仅项目名和版本号的占位正文。不要将 GitHub 自动生成的 PR 清单直接作为最终说明；必要时可作为核实线索。
- 使用 Write 保存为新的 UTF-8 `release-notes.md`，放在独立资产目录或临时目录，不混入 ZIP 或修改用户现有文件。

## 发布工具合同

- `release_tool.py publish` 在预演和正式发布时都必须提供 `--notes-file`，使用非空 UTF-8 常规文件。说明文件不打包、不作为第三个资产上传。
- 预演结果展示 `notesFile`、完整 `notes` 及 `--notes-file` 创建命令，供检查；说明有变动必须重新预演。
- 正式发布读取正文快照，通过 `--notes-file` 传给 GitHub。发布前后检查 draft/正式正文匹配，比较只忽略 CRLF 与末尾空白。缺失/不符则报错，保留 draft，不盲删重建。

## 修订已发布说明

用户明确要求补充/修订指定 Release 的说明即授权该正文编辑，不代表允许修改版本、tag、资产、渠道或其它 Release。只使用 `gh release edit --notes-file`，不得重新执行发布或重传资产。

1. 保存快照：`gh release view vX.Y.Z --repo OWNER/REPO --json body,isDraft,isPrerelease,tagName,targetCommitish,assets > /tmp/release-vX.Y.Z-before.json`，记下 tag commit 和资产 ID/名称/大小/digest。
2. 已有实质说明时保留有效内容，只补充或修正本次范围。依据已发布 tag 的提交撰写，不能把 tag 之后的提交写成本版功能。
3. 编辑前再次回读正文并与快照比对；若他人已修改，保留双方有效内容、重新核实，不直接覆盖。执行 `gh release edit vX.Y.Z --repo OWNER/REPO --notes-file /absolute/release-notes.md`。
4. 重新读取 Release，比较正文、正式状态、tag commit 和资产元数据。只有正文按预期变化、其余项不变才算成功。
5. 按 [修订与最终报告](update-log-delivery.md#6-修订与最终报告) 分别检查已授权的镜像正文及客户端刷新能力。GitHub 正文已修改不等于 GitCode、包内日志或已有缓存同时改变；不得通过覆盖发布资产或删除用户缓存掩盖差异。
