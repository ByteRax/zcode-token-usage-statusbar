# Review → Fix → Merge

对**当前会话产生的代码变更**按授权范围执行：多 subagent 并行审查 → 修复 → 循环验证；若明确授权完整收口，再提交 → 推送 → 创建或更新 PR → 等待检查 → 合并到 `main`。

## 授权边界

- 用户在当前会话要求“review 然后合并”“review 并合并”“审查后合并”等，或明确要求将本次变更合并到 `main`，或显式调用本 Skill 且未限制操作，即授权完成当前会话代码变更收口所必需的提交、推送、创建或更新 PR 和合并；未指定目标时按本 Skill 目标 `main` 执行。权限和仓库策略仍然有效，无需重复确认。用户明确给出的限制优先于调用名称，不得用其他动作绕过；改动或目标仓库归属不明时仍须停下澄清。
- 仅请求“持续修复直到可以合并”或其他只要求达到可合并状态的措辞，不视为授权提交、推送、创建 PR 或合并；完成审查和验证后停止并报告。如只明确授权部分步骤，就停在授权边界；例如禁止推送时即使远端已有该提交，也不由此推断可创建或合并 PR。普通的纯审查请求不触发本流程。
- 不因 Skill 自动匹配、以前的授权或仓库权限推断本次请求授权了外部写入。涉及额外审批或权限受限时，在该步骤停止并报告。

**"没有问题"的口径**：指在可获取的上下文和实际执行的检查范围内，没有发现尚未解决的问题。完成时如实陈述这个范围，不声称代码绝对没有缺陷。

## 红线（全程有效）

1. **改动归属**。只提交本次任务相关变更。不把工作区中与任务无关的改动、用户已有改动或来源不明的改动纳入提交、覆盖、重置或删除。无法可靠区分归属时，保留现场，说明需要澄清的具体内容。
2. **不为过关造假**。不删除有效测试、不降低检查标准、不隐藏异常、不绕过项目规则来让检查通过。修复必须真实解决问题，而不是让报错消失。
3. **不直推 main**。当前在 `main` 上时先创建工作分支再提交。不绕过分支保护、必需审批、状态检查或其它仓库策略。
4. **合并安全优先**。遇到环境限制、外部依赖不可用、无法验证的问题，或需要明显超出当前任务范围的改动：说明原因和影响；若影响合并安全性或必要检查，停止合并并报告。
5. **不造空流程**。当前没有代码变更时，先确认当前分支是否已有属于本次任务的未合并提交或 PR；不为走完流程制造空提交或无意义 PR。
6. **并行 subagent 读写隔离**。并发派发的审查/验证 subagent 严禁修改共享工作树、暂存区、分支引用或执行远端写入；写操作（应用修复、`sync_plugin.py`、提交、推送、PR 创建/更新与合并）统一由主 agent 收口。

## 并行多 Subagent 协同策略

自己复核自己容易遗漏盲区，串行审查与测试又会拉长周期并撑爆主上下文。除极小改动外，审查与验证阶段应**同一轮并行派发多个独立 subagent（单轮 Fan-out）**：

| 变更规模 | 同轮并行 subagent 配置 |
|---|---|
| 单文件文案/注释微调，无行为变化 | 0–1 路：主 agent 自审 diff + 定向检查 |
| 常规功能或修复（约 2–8 个文件） | **2–3 路并行**：① 正确性、边界与回归审查；② 变异式测试审查（挑死测试/漏网断言）+ 全量测试执行；③ 文档、插件副本同步与冷文件判定 |
| 跨模块、协议/契约变更、主进程冷文件或复杂 UI/状态机 | **4–10 路并行专项切片**：按审查维度或文件域横向拆细（正确性与契约、状态机/并发/DOM 交互、变异式测试猎杀、安全与权限边界、文档/副本与发版素材核对），每域一路同轮并发深审；超过用户全局子代理策略默认上限的拆细仅限确有必要时使用，不为走流程多开 |

### 并行派发与隔离纪律

1. **同轮并发启动，每轮全新实例**：同一轮的所有 reviewer / 验证 subagent 必须在**同一次工具调用轮次内并发派发**，不要串行逐个等待；进入下一轮复审时**新开 subagent**，不续用上一轮 agent，确保独立视角。
2. **简报自包含**：subagent 看不到主对话，简报须显式给出：工作目录绝对路径、基线（如 `fork/main`）与被审范围（候选 SHA 或明确的文件/diff 范围）、本次需求与改动摘要、需对照的 `AGENTS.md` 及 `.zcode/rules/*.md` 具体章节、已知环境基线红灯，以及统一定级标准（与 `zcode-issue-pr-resolver` 的 [review 简报](../zcode-issue-pr-resolver/references/review-brief.md)公共前言同一口径：`BLOCKER`＝按字面执行会破坏仓库/远端/凭据，或使已声明的安全控制被绕过且无补救；`MAJOR`＝会得到错误结果或做错事，或绕过某项已声明的保护，且给得出可复现步骤或推演依据；`MINOR`＝措辞、归类、可读性、低概率边角、改进建议或既有问题，附 `file:line` 与修复建议）。
3. **严格只读与临时克隆隔离**：
   - 并行 reviewer 在原工作树/候选工作树内**只使用只读 git 子命令**（`diff`、`log`、`show`、`rev-parse`、`--no-optional-locks status` 等），禁止 `checkout`、`reset`、`stash`、`commit` 或写文件。
   - 需要修改代码验证猜想或做变异测试（把实现改坏看测试是否变红）时，subagent 必须在各自独立的 `T=$(mktemp -d)` 下执行 `git clone --no-hardlinks <工作树路径> "$T/r" && git -C "$T/r" remote remove origin`（若包含未提交改动，先将目标文件拷入 `$T/r`），在私有副本内实验并在结束前清理 `$T`。跑 Python 一律加 `-B` 与 `PYTHONDONTWRITEBYTECODE=1`。
4. **并行验证分流**：可将耗时检查拆给不同 subagent 并行执行（例如一路跑 `node --test tests/*.test.cjs` 与 `node --check`，另一路跑 `python3 -B -m unittest discover -s tests -p 'test_*.py'` 与 `python3 sync_plugin.py --check`），主 agent 汇总退出码与失败明细。
5. **主 agent 统一收口修复**：主 agent 收集所有并行 subagent 的报告后去重、定级并统一修改代码（或仅在完全无交集的文件域让 subagent 产出补丁建议，由主 agent 审阅落盘并统一跑 `python3 sync_plugin.py`），避免多 agent 并发写同一文件或争抢插件副本同步。

## 流程

### 1. 确定审查范围与仓库状态

先检查：

- 当前目录是否 Git 仓库；当前分支、所有远程及 fetch/push 地址、默认分支，以及**目标仓库**的 `main` 是否存在且允许作为 PR 目标。默认分支不必是 `main`；目标 `main` 不存在或不允许合并时停止，不擅自改目标。
- 工作区和暂存区状态，包括未跟踪文件；当前会话修改过哪些文件，以及当前分支相对目标仓库最新 `main` 的完整提交和差异。
- 项目的开发规范（如 `AGENTS.md` / `.zcode/rules/*.md` / `CLAUDE.md` / `CONTRIBUTING`）、测试要求和 PR 要求。

审查范围优先包括当前会话产生的全部代码变更，以及理解和验证这些变更所必需的相关代码。准备 PR 时，还须核对整个 PR 相对目标仓库 `main` 的提交和 diff：存在无关或归属不明内容就隔离，无法安全隔离则停止。

### 2. 并行多维度审查代码

按上方「并行多 Subagent 协同策略」在同一轮并发派发多路独立只读 subagent，结合项目上下文分维度审查与本次变更相关的问题：

- **功能与契约（正确性路）**：功能是否满足当前会话需求；逻辑错误、边界条件、异常处理、fail-closed 语义和潜在回归；接口、类型、兼容性和配置契约（对照 `AGENTS.md` §5 及对应 `.zcode/rules/*.md`）。
- **并发、性能与安全（专项/安全路）**：定时器/监听器/子进程生命周期与清理、竞态条件、资源管理；安全、隐私、数据完整性、外部输入转义及权限边界。
- **测试有效性（变异测试路）**：测试是否覆盖关键行为与新增分支；是否存在源码字符串匹配冒充行为断言、未收集到的死测试，或在临时克隆中改坏关键分支仍绿的漏网断言。
- **文档、副本与发版面（一致性路）**：`python3 sync_plugin.py --check` 副本同步、`overlay.js` 的 `VERSION` 代际台账、文档同步需求；用户可见面是否变化（入口、默认值、配置键、文案，以及是否命中冷文件需要完全重启）——这些要写进第 4 节的「发版说明素材」，并同步文档与 README。

主 agent 汇总各路 subagent 报告，按影响和严重程度（`BLOCKER` → `MAJOR` → `MINOR`）去重排序，优先修会导致错误、数据损坏、安全风险或功能不符合需求的问题。避免与任务无关的大规模重构和纯风格改动。

### 3. 修复、并行验证、复审循环

1. **集中修复**：由主 agent 修复发现的 `BLOCKER`/`MAJOR` 及合理的 `MINOR` 问题（若涉及共享文件，修改根源码后执行 `python3 sync_plugin.py`）。
2. **并行验证**：运行与改动相匹配的测试、类型检查、静态检查或构建——以项目文档约定的命令为准，不虚构项目不存在的命令。耗时的全套回归（Node 测试套件、Python 测试套件、语法与副本检查）可通过并行只读 subagent 同轮分流执行。
3. **新一轮并行复审**：对修复后的变更**新开一轮并行 reviewer subagent**（简报中附上上一轮发现的问题摘要，要求重点攻击本轮修复本身及相邻路径，检查是否引入新回归）。
4. 若发现新的、属于本次任务范围的问题，回到第 1 步。
5. 重复以上过程，直到某一轮所有并行 reviewer 均确认在实际审查范围内没有尚未解决的问题（无 `BLOCKER`/`MAJOR`，`MINOR` 已修或有明确不修理由），且相关必要检查全部通过。若连续 3 轮仍有 `BLOCKER`/`MAJOR` 或修复来回震荡，停止合并并向用户报告原因与当前现场。

### 4. 提交并创建 PR

验证通过且相应操作已获授权后（写操作均由主 agent 串行执行）：

1. 明确目标平台、仓库的 host/owner/repo、base=`main`、head 仓库及分支，核实实际 fetch/push URL；多个目的地须逐一确认都在本次授权范围内。目标或归属不清时停止，不能只凭远程名或同名 `main` 猜测。
2. **推送前**确定拟用 head、目标仓库和 `main`，查询该 head 关联的开放 PR 及自动合并/队列状态：已有本任务 PR 时核实身份、完整历史和目标并优先更新；没有时确认没有关联的不相关开放 PR，再推送并创建。存在不相关 PR 时不要更新它，从正确基线隔离本次变更。关联 PR 已启用自动合并、处于合并队列或状态无法确认时停止推送，不擅自取消他人的设置。新 PR 优先使用任务专属 head；更新已有 PR 时评估推送期间目标及自动合并状态被并发修改的风险，无法通过平台保护或隔离消除可能导致未经授权合并的风险时停止推送。
3. 保留原工作区、当前分支和已有暂存内容；用独立工作树或隔离索引配合独立引用/游离提交构造候选提交，不能只隔离索引却移动共享 HEAD。仅纳入本任务变更，核对实际提交树、完整提交序列及相对目标 `main` 的 diff，确认无无关内容。**在干净的隔离工作树检出候选 SHA 并运行必要检查**（可并行派发只读验证 subagent 针对该隔离工作树的固定候选 SHA 同时跑各套测试与检查），核对未提交、未跟踪及忽略文件不会影响检查，记录结果和 SHA；若采用其他受测环境，须证明受测文件树与候选树一致且无影响结果的残留。候选内容变化后重新审查并验证，无法可靠验证则停止。
4. 推送前再次核对关联 PR 状态和目标，按已核实的目的地用经过验证的不可变 SHA 明确指定目标 ref 推送，并核对远端实际 SHA；不要按可能被并发移动的本地分支名推送。多 push URL 不是原子操作，逐一核对远端结果，部分成功则停止并报告已成功和失败的目的地，不假设整体失败等于没有外部写入。不强推或覆盖他人变更。
5. 显式指定目标仓库与 `main` 创建或更新 PR。标题、描述及项目要求的模板/标签应准确说明问题、解决方式和实际完成的验证，并按下一小节带上「发版说明素材」块。

#### PR 描述：发版说明素材

发版时 `zcode-github-release` 会读 PR 正文来撰写更新说明（见其 [release-notes.md](../zcode-github-release/references/release-notes.md#核实范围)）。PR 描述除问题与根因、改动、验证、未验证项外，须附下面的块，让发版时不必重读 diff；纯内部、测试、文档的 PR 也要写，明确声明「无用户可见变更」，不要留空：

```markdown
### 发版说明素材
- 类型：新增 / 修复 / 改进 / 无用户可见变更（纯内部、测试或文档）
- 用户可见条目：
  - 新增：[入口 + 默认行为，一行]
  - 修复：修复……的问题
- 重启要求：需要完全退出 ZCode / 无需重启（附冷文件 diff 命令及结论）
- 升级注意：[入口删除或改名、默认值或配置键变化、需迁移的用户；无则写「无」]
- 成熟度：[涉及 `unverified` 适配器或未实机验收的平台时原样标注；无则省略]
```

- 条目对齐 [条目写法与官方对照](../zcode-github-release/references/release-notes.md#条目写法与官方对照)：一行内写清「谁受益 + 变了什么」，修复写症状（「修复……的问题」「……不再……」），新增先写入口再写默认行为，机制与公式放后半句。不要拿 PR 号、`vNNN` 代际号、内部模块名当主语；同一主题的多个提交合并成一条。
- 重启要求用 [pre-publish-checks.md「重启要求」](../zcode-github-release/references/pre-publish-checks.md#重启要求)的 diff 命令判定，基线改为目标 `main` 的合并基（`git diff --name-only <目标main>...<head> -- <冷文件清单>`）。清单以该文档为准，这里不复制。命中冷文件就写「需要完全退出」，只涉及热文件时也要先按 `AGENTS.md` §3 确认加载路径，才能写「无需重启」。
- 这个块是作者自述，不是证据：发版时仍要对照 diff 核实，所以这里只写能被 diff、测试或文档证实的内容，不写计划中或未提交的能力。

### 5. 等待检查并合并

在当前用户明确授权审查并合并时，允许并自动执行对自己 PR 的 AI 自审：由独立于实现过程的**多路并行 review subagent** 绑定最终候选 `head SHA` 审查完整 diff、边界与测试，并按第 3 节修复、复审，记录各路审查结论和对应 head SHA。作者也可自审；但 AI 自审结论不等于平台上的独立批准。若平台允许当前身份批准该 PR，且已审查整个变更、没有未解决问题，提交真实的 `APPROVE` 审查（GitHub 可使用 `gh api repos/OWNER/REPO/pulls/NUMBER/reviews -f event=APPROVE -f commit_id=SHA`），回读审查状态、审核者和提交 SHA，并确认平台将其计入所需批准。head 或 base 改变后重新评估审查有效性。

如果当前身份不能合法批准（例如 GitHub 的 PR 作者不能批准自己的 PR）、权限不足、批准未计入或规则状态无法确认，则停止并明确要求具备权限的独立审查者批准；不得切换或冒用未经用户授权的身份、伪造审查、修改保护规则或使用管理员绕过。用户授权合并不等于授权代替独立审查者做出批准。

1. 核对 PR 的目标仓库、`main`、head 仓库/分支、整个变更范围和合并状态，记录实际审查并验证的 head SHA。头提交、目标或 diff 变化时重新审查、验证并等待对应检查。
2. 等待与已审查 head 及当前目标分支关联的 PR/MR 必需 CI、审批和其他合并条件；检查不可用、缺失、失败或仍在等待时不得当作通过。GitHub 可用 `gh pr checks --watch` 查看检查，再结合 PR 状态和仓库规则核实必需项；GitLab 可用 `glab ci status --wait` 等待，但须通过 MR 状态和流水线身份核对，不能只凭分支流水线认定通过。合并结果流水线或合并队列可能测试临时合并提交，其 SHA 不必等于 head；要核对平台显示的 head/base 关联与规则，不以 SHA 不同直接判失败或当作已通过。只在入队后才创建的必需候选检查，按平台规则分阶段等待：入队前先满足其余前置条件，入队后继续等待候选检查与最终状态，不能将尚未产生的检查视为已通过。
3. 检查失败时分析并修复属于本次变更的问题；冲突先分析，只在能安全判断且不丢失他人改动时解决。每次修复或解决冲突后都返回第 3 节重新审查、验证完整 diff，并按第 4 节对更新后的候选提交重新验证；再核对推送与 PR 身份、推送并等待新提交的检查。无法安全解决或必要检查不可用时停止报告。
4. 合并前再次核对目标仓库、`main`、PR 范围、审批、检查及 head SHA；同时回读 PR 描述，确认「发版说明素材」与最终 head 的 diff 一致（修复循环可能改变了用户可见行为或冷文件命中），不一致先更新描述再合并；使用平台的条件合并能力绑定已审查 SHA（例如 GitHub `gh pr merge --match-head-commit <SHA>`、GitLab `glab mr merge --sha <SHA>`）。遵循仓库实际的保护、审批和合并规则，不使用绕过权限。检查期间若发现 head、目标或相关条件变化，停止当前合并，重新审查验证。
5. head 条件不一定锁定目标 ref 或 base 提交；异步自动合并和队列也可能在发起后变化。优先使用仓库已有的严格 base 检查、合并队列候选检查及权限隔离；核实这些保护实际覆盖的范围。发起自动合并或入队前，核实平台在 head 更新时能阻止未审查提交自动合入，无法确认则停止并报告；不能只靠轮询或事后取消消除竞态。本流程已开启自动合并或入队后发现变化或必须停止时，撤销本流程开启的自动合并或入队并确认；不能撤销或确认时明确报告仍可能自动合并。对平台无法原子保护的其他竞态，如目标 ref 或 base 在最后核对后变化，明确说明剩余风险，不得声称绝对无竞态。若这一限制影响合并安全性或必要检查，停止并报告；否则可按仓库允许的流程继续，合并后核对实际目标、结果和合并提交标识。入队不是已合并，继续等待候选检查和最终状态；不能确认则报告未完成。
