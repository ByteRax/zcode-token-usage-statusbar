# 多 Subagent 并行执行手册

只在确实存在可并行的工作流时加载本文件。目标是缩短关键路径，不是最大化 Agent 数量。

## 1. 选择并发策略

| 任务形态 | 建议配置 | 处理方式 |
| --- | --- | --- |
| 单一函数/单文件、小修复 | 主代理 1 个（必要时另设只读审查） | 不强制并行，直接改代码 |
| 中等：跨 2～3 个模块、已有验收标准 | 主代理 + 3～4 个子代理 | 先并行查证，再按文件边界并行实现 |
| 大型：多个参考项目/多个目标模块/多个平台 | 主代理 + 5～8 个子代理 | 任务 DAG + 按波次派工；独立子任务足够时可扩至用户指定上限（如 10） |
| 多个代理都必须改同一个核心文件 | 1 个该文件写入者 + 多个只读研究/审查者 | 不允许为了并行强行拆分写入 |
| 没有可用 Subagent/Team 调用工具 | 主代理串行执行 | 不伪造已派工/已完成信息 |

这些是初始建议，不是硬编码配额。并发上限取运行环境允许值、独立任务数、用户要求三者的合理交集；如果代理调度开销超过实际任务，主动减少子代理。允许按波次重用已经完成的代理，减少重复初始化和搜索。

## 2. 以依赖图组织工作，而不是按角色排队

```text
P0: 仓库状态/权限/范围检查（主代理）
                   |
       +-----------+-----------+------------------+
       |           |           |                  |
 A: 参考源码   B: 目标架构   C: 平台/许可     D: 测试/验收
       |           |           |                  |
       +-----------+-----------+------------------+
                   |
        P1: 合并证据、冻结公共接口契约
                   |
          +--------+--------+----------+
          |        |        |          |
      E: 核心   F: UI    G: 适配器  H: 独立测试
          |        |        |          |
          +--------+--------+----------+
                   |
          P2: 主代理集成 + 构建
                   |
         I: 独立审查 / 定向复测
                   |
                最终交付
```

- 分析阶段允许提前完成的代理立即返回结果，主代理可据此继续**不依赖其余结果**的准备工作。
- 只有核心契约（接口名、数据结构、事件、错误语义、目标文件分工、验收项）达成一致后，才同时放行会互相依赖的编码任务。
- 实现阶段按真正独立的模块派发，不强制 E/F/G/H 都存在；若 UI 需要等核心接口，先冻结类型/契约或推迟 UI。
- 质量审查和实现可以交错：只读代理可审核已完成的独立补丁，但最终集成测试与回归必须基于同一份合并快照。

## 3. 任务 DAG 与文件所有权

大型项目建议在**工作区外或受控临时目录**维护 `task-plan.json`，避免未经授权修改仓库文档。示例见 [task-plan.example.json](task-plan.example.json)。可运行 `python scripts/validate_task_plan.py task-plan.json` 检查任务依赖与潜在写入冲突；此脚本只检查计划，不会创建或执行 Subagent。

每个任务至少指定：唯一 ID、phase、mode、depends_on、writes、目标、验收。`writes` 使用目标仓库相对路径；`src/foo/` 表示整个目录的写入所有权，`src/foo.ts` 表示精确文件。确保没有两位可并发执行者对同一目录或文件写入。对共享文件（路由注册、依赖锁文件、入口索引、全局配置），统一由主代理负责集成，其他代理提交修改建议或补丁，不直接写。

如果必须改同一个文件：

1. 首选将可独立逻辑提取为新模块，保留主代理修改公共入口。
2. 次选按依赖顺序串行修改，其他代理只负责只读分析/测试用例设计。
3. 可使用独立 Git worktree 分别生成补丁，但由主代理审阅和逐个合入；**不同 worktree 不代表合并时没有冲突**。

不要由多个代理并行运行 `npm install`、迁移数据库、修改锁文件或覆盖生成文件。公共依赖更新、全局配置和跨模块契约变更交给主代理。

## 4. 并行操作中的 Git 安全

- 记录目标 `HEAD`、分支及 `git status --short`，识别已有未提交修改。工作树不干净时，**不**强制 reset/clean、自动 stash 或盲目覆盖。执行前确认可安全隔离的路径。
- 参考仓库保持只读，在主项目之外处理；使用固定 commit/tag 取证，避免不同代理读到不一致版本。
- 支持 Git worktree 的环境，写入代理可各用独立 worktree（应基于已核验的目标基准提交）；无 worktree 则只给互不重叠的文件写权限。
- 工作树中已有用户修改且无法安全在基准工作树合并时，子代理输出补丁和冲突说明，主代理人工审阅后再应用。
- 收集子代理产物时，检查补丁的真实基线、改动路径、非预期文件、二进制/锁文件、删除以及 untracked 文件。避免 `git checkout .`、`git reset --hard`、不受控 `git clean`。
- 只在用户授权时提交/推送/建 PR/合并；不要为了方便跨 worktree 集成就默认提交到远端。

## 5. 减少重复搜索与 Token 开销

- 主代理只给每位代理必要上下文：目标、仓库位置、固定版本、已知入口、禁止区、报告结构；不要向所有代理重复发送完整源码或冗长会话历史。
- 每位分析代理只返回 5～12 条最重要证据和下一步需要读取的位置，而非粘贴整个源文件。
- 有证据缺口时**定向补查**，不让全部代理重新扫描同一个仓库。
- 控制研究范围：优先 `grep/rg`、符号搜索、定义/引用/测试；找到足够证据即可停止扩大搜索。
- 针对未通过的一个失败，只指派 1 位所有者修复，审查代理提供只读定位；避免多代理同时修同一处。
- 测试任务按照 scope 分组：模块测试可各自跑；全量测试、跨模块构建由主代理在集成后跑一次，增量修复后只复测受影响项。
- 若某子任务迟滞，先判断是否阻塞关键路径；可让主代理推进其他可独立部分，只有实际阻塞时才定向接管/改派。

## 6. 双阶段质量闸门

**代理局部交付**（每位写入者都需给出）：
- 精确的写入文件清单（不得超出所有权）；与冻结的接口契约一致。
- 关键实现、边界和限制，测试命令及结果；引用真实错误日志，不写“预计通过”。
- 源码借鉴与许可证风险、剩余 TODO、需主代理处理的公共文件建议。

**主代理统一集成**：
- 确认所有依赖任务已交付，集成的代码来自已检查产物。
- 重新检查全局接口、路由/注册/配置、类型、资源释放、平台条件与许可；不得只将代理“完成”当作验收通过。
- 按影响面执行 lint/typecheck/unit/integration/build/E2E，跨端仅报告真实验证结果。
- 让独立审查者只读审阅**最终集成 diff**，并对高严重度问题按文件所有权定向修复后重验。
- 统一报告已完成/部分完成/阻塞的子任务，不以子代理数量表示质量或速度提升。

## 7. 何时暂停扩大并行

任一条件成立就缩减并发：重复搜索明显、文件所有权频繁冲突、公共接口反复变化、依赖链严重串行、资源/工具限流、测试互相污染、成本超过进展。不得使用“等待所有代理”替代主代理主动集成；也不得在关键证据缺失时贸然编码。任务拆分只是提速手段，正确性和用户已有工作优先。
