# 审查技能的子代理并发上限

## 规则

审查技能提供的并发数量只是按任务规模的建议，必须服从当前会话和用户明确规定的并发上限；不得因任务复杂自行突破上限。需要更多审查维度时，合并切片或分批执行。本 spec 适用于仓库内所有带并行审查派发的技能（`zcode-review-fix-merge`、`zcode-issue-pr-resolver`，以及 `zcode-github-release` 阶段 A 核查与发布后回读的只读 subagent）；各技能正文与此处不一致时，以本 spec 为准。

### 派发节奏

同时有多个默认模型（随主会话，目前是 GLM-5.4）的审查 subagent 在跑时，模型服务会限流：每一步都要等几分钟才出第一个字，同时跑的越多越慢。派发时按下面的规则：

1. **默认模型的审查员一次只跑一路。** 一路交回报告后再派下一路。别的会话同时跑的审查员占同一个名额。
2. **机械活交给 `review-runner`。** 它是固定用 GLM-5.3-FlashX 的项目代理（`.zcode/agents/review-runner.md`），不受上面那条排队影响，可以和默认模型的审查员同时跑，最多 2 路。它按给定清单分批跑变异、跑全量测试、跑副本与清单检查（发版的升级链解包与多端回读比对同理），只执行、不裁决：它报的「变异存活」「没跑到」，主 agent 在干净副本复核后才写进报告。
3. **判断类审查留在默认模型。** 正确性与契约、状态机与并发、安全边界，以及变异清单的设计，都由默认模型的审查员做。
4. **小改动不派审查员。** 单文件文案或注释、只改测试或文档的增量复审，由主会话直接审。
5. **满足条件才恢复同轮并发。** 最近 30 分钟本机默认模型的 subagent 请求不少于 5 条，且「等第一个字」的中位数低于 5 秒，这时可以在同一次工具调用里并发派发默认模型的审查员。没有样本或不满足，就按第 1 条逐路派发。查法见「负载判据」。

### 单路上限、等待与刹车

6. **每一路都有上限。** 判断类审查员每路最多 12 次工具调用。要在私有副本里批跑变异的，不自己跑完：把变异清单（每批不超过 20 条，写明编号、写法、预期变红的用例）交给 `review-runner`。简报里写死上限，并写明「多条命令合并进一次调用，到上限立刻出报告，没查到的逐条写未查」。
7. **前台跑完再回报，阻塞等，不 sleep 轮询。** 子代理不得启动后台任务后干等（后台任务跑完不会唤醒它）。主 agent 用 `TaskOutput` 等报告（`block: true`，`timeout` 不超过 600000 毫秒），不用 `sleep` 去轮询它的草稿文件。
8. **挂住就止损。** 一路超过 30 分钟没有任何新的工具调用完成，或总用时超过 60 分钟，先 `TaskStop`，再 `SendMessage` 下「不再调用任何工具，凭已有证据出报告」。只 `TaskStop` 一次不一定停得住，第二条消息才会以恢复方式重启它。
9. **报告只回结论。** 每路报告不超过 30 行：BLOCKER、MAJOR、MINOR 各几条，每条一行「file:line + 一句依据 + 修法」，最后单独一行结论。不复述 diff，不贴大段代码，不写检查过程。长证据写进它自己的临时文件，报告里只给路径，主 agent 决定是否读。
10. **审查轮数封顶。** 每个 issue 或 PR 的判断类审查默认最多 2 轮。第 2 轮之后仍有 BLOCKER 或 MAJOR，就停下来报告，用户点头才开第 3 轮。MINOR 不单独触发新一轮：修掉，或写明不修的理由。
11. **完成通知不自动开新一轮。** 子代理的完成通知会唤醒主会话开新的一轮。这一轮只做四件事：收报告、汇总定级、修 BLOCKER 与 MAJOR、收尾（提交、更新 PR、回复）。没有待修项，或者已经是第 10 条的最后一轮，就直接汇报并结束，不再派审查员。
12. **派发前先报预计用时。** 按下面的负载判据估：通畅时判断类每路约 10~15 分钟，拥挤时 30~60 分钟。把预计用时告诉用户再派；用户说了时限的，按时限裁剪审查范围。
13. **限流失败后先看拥堵再续跑。** 上一轮因限流失败（`rate_limited`，重试 10 次后放弃）时，不立刻续跑：先 `TaskStop` 在途的默认模型子代理，再跑一次负载判据。近 30 分钟主会话的限流比例不低于 20% 就是拥挤：告诉用户，建议错峰或只跑主会话，等用户决定。

### 负载判据

在仓库根运行，只读本机用量库，几秒出结果：

```bash
python3 -B scripts/model_load.py            # 近 30 分钟
python3 -B scripts/model_load.py --minutes 60
```

它输出这段时间里主会话的请求数与被限流的比例、默认模型子代理请求的条数与「等第一个字」的中位数、FlashX 子代理的中位数，以及一行结论。判定用的是上面的数字：第 5 条（子代理请求不少于 5 条且中位数低于 5 秒，可同轮并发）、第 12 条（中位数低于 5 秒为通畅）、第 13 条（主会话限流比例不低于 20% 为拥挤）。没有样本时写「无法判定」，按不满足处理。

### 依据

2026-11-23 至 11-26 在本机用量库 `model_usage` 上量的结果。

一周的总量（主会话 324 轮，共 89.4 小时）：模型生成 43%，等首字里的限流重试 15%，等子代理 12%，工具执行 16%。另有 160 轮（49%）由后台通知或 goal 续跑触发，共 23.4 小时。主会话 `sleep` 等审查员 2.2 小时。长轮次里 98% 的输出是推理（请求体是 `effort: max`），72% 的步骤只调用一个工具。

GLM-5.4 子代理的完成请求，等第一个字的中位数：

| 情况 | 等第一个字（中位数） |
|---|---|
| 繁忙时段，当时没有别的 GLM-5.4 子代理在跑 | 3.6 秒（32 条，样本少） |
| 繁忙时段，同时另有 1 个、5 个以上 | 92 秒、171 秒 |
| 同周，按请求开始时同模型在途数分组：0~2 个、8 个以上 | 1.9~3.2 秒、177.6 秒 |
| 凌晨 2–7 点，冷启动 3.2 万 token 全部未缓存 | 1.8 秒 |
| 同周，改用 GLM-5.3-FlashX 的子代理（861 条请求共 2.8 小时） | 1.5 秒 |
| 繁忙时段，主会话自己的请求 | 5.0 秒 |

- 子代理请求的总耗时里，75% 在等第一个字，25% 在生成。缓存命中约 90%，从第 2 步起每步只新算本步新读的内容。所以「审查员带着很大的 AGENTS.md」不是慢的原因：给它瘦身，每次审查只省 1–2 秒。
- 同一周默认模型的子代理发了 2464 条请求，共 137.3 小时；FlashX 是 861 条、2.8 小时。
- **主会话为什么几乎不受影响（11-26 查明）**：引擎给每个模型请求设了本地准入排队。主会话的请求不排队直接发，超限被服务端拒（1302）后重试；子代理的请求要先排队，等在飞数低于上限才发（ZCode 源码仓 `create-app.ts` 里的 `workflowConcurrencyGovernor.observer()` 与 `sessionSubagents()`，按 v3.18.2；4.0.0 的引擎包里仍含同一套代码）。请求的开始时间记在排队之前，所以子代理「等第一个字」里包含本地排队。这个上限按 CPU 核数起算（本机 14 核是 12），高于账号能承受的数量；主会话每被拒一次，上限还会被压低。结论不变：少派、逐路派、机械活换 FlashX。
- 主会话被限流的次数随并发涨：同模型在途 0 个时 5.5%，3 个以上 23%~33%。同一时间跑的主会话越多也一样：旁边没有别的会话时 7.7%，有 1 个时 17.9%。
- 智谱文档写明：并发上限按账号、按模型各算，套餐在低峰期并发更高；超限报 1302 或 1305（[速率限制](https://docs.bigmodel.cn/cn/api/rate-limit)）。

限流政策会变。审查又明显变慢时，按「负载判据」复测，不要凭印象改规则。

### 复测

`scripts/model_load.py` 把窗口内的请求按 10 分钟一行列表（主会话请求数与限流比例、子代理请求数与等首字中位数）。要查得更细，就只读查 `model_usage`：把 `first_token_at - started_at` 分桶，再按小时和「请求开始时同模型还有几个请求在途」交叉。库的默认路径见 `AGENTS.md` §5；被改过时用 `--db` 指定。

## 验收

- 复杂任务建议不超过六路，且明确服从更严格的当前上限。
- 既有审查维度和独立复核要求保持不变。
- 不满足「恢复同轮并发」的条件时，默认模型的审查员同一时刻只有一路在跑；`review-runner` 不超过 2 路，不承担判断类审查。
- 主 agent 的报告写明本轮用的节奏（逐路或同轮并发）和判定依据。
- 简报里写明工具调用上限、前台跑完再回报、报告不超过 30 行；主 agent 派发前给出预计用时。
- 判断类审查默认最多 2 轮；第 3 轮要有用户点头。
- 子代理完成通知触发的新一轮只做汇总、修复、收尾；没有待修项就结束。
- `zcode-github-release` 的只读核查按同样的节奏派发：全量测试与静态检查、升级链解包、清单与正文的回读比对交给 `review-runner`，台账、冷文件与更新说明的核实留在默认模型的 subagent。
