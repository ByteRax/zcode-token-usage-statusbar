# 审查技能的子代理并发上限

## 规则

审查技能提供的并发数量只是按任务规模的建议，必须服从当前会话和用户明确规定的并发上限；不得因任务复杂自行突破上限。需要更多审查维度时，合并切片或分批执行。本 spec 适用于仓库内所有带并行审查派发的技能（`zcode-review-fix-merge`、`zcode-issue-pr-resolver`，以及 `zcode-github-release` 阶段 A 核查与发布后回读的只读 subagent）；各技能正文与此处不一致时，以本 spec 为准。

### 派发节奏

同时有多个默认模型（随主会话，目前是 GLM-5.4）的审查 subagent 在跑时，模型服务会限流：每一步都要等几分钟才出第一个字，同时跑的越多越慢。派发时按下面的规则：

1. **默认模型的审查员一次只跑一路。** 一路交回报告后再派下一路。别的会话同时跑的审查员占同一个名额。
2. **机械活交给 `review-runner`。** 它是固定用 GLM-5.3-FlashX 的项目代理（`.zcode/agents/review-runner.md`），不受上面那条排队影响，可以和默认模型的审查员同时跑，最多 2 路。它按给定清单分批跑变异、跑全量测试、跑副本与清单检查（发版的升级链解包与多端回读比对同理），只执行、不裁决：它报的「变异存活」「没跑到」，主 agent 在干净副本复核后才写进报告。
3. **判断类审查留在默认模型。** 正确性与契约、状态机与并发、安全边界，以及变异清单的设计，都由默认模型的审查员做。
4. **小改动不派审查员。** 单文件文案或注释、只改测试或文档的增量复审，由主会话直接审。
5. **满足条件才恢复同轮并发。** 最近 30 分钟本机默认模型的 subagent 请求不少于 5 条，且「等第一个字」的中位数低于 5 秒，这时可以在同一次工具调用里并发派发默认模型的审查员。没有样本或不满足，就按第 1 条逐路派发。查法见「复测」。

### 依据

2026-11-23 至 11-25 在本机用量库 `model_usage` 上量的结果，对象是 GLM-5.4 子代理的完成请求（2205 条）：

| 情况 | 等第一个字（中位数） |
|---|---|
| 繁忙时段，当时没有别的 GLM-5.4 子代理在跑 | 3.6 秒（32 条，样本少） |
| 繁忙时段，同时另有 1 个、5 个以上 | 92 秒、171 秒 |
| 凌晨 2–7 点，冷启动 3.2 万 token 全部未缓存 | 1.8 秒 |
| 繁忙时段，改用 GLM-5.3-FlashX 的子代理 | 1.5 秒（178 条） |
| 繁忙时段，主会话自己的请求 | 5.0 秒 |

- 子代理请求的总耗时里，75% 在等第一个字，25% 在生成。缓存命中约 90%，从第 2 步起每步只新算本步新读的内容。所以「审查员带着很大的 AGENTS.md」不是慢的原因：给它瘦身，每次审查只省 1–2 秒。
- 智谱文档写明：并发上限按账号、按模型各算，套餐在低峰期并发更高；超限报 1302 或 1305，文档没说会自动排队（[速率限制](https://docs.bigmodel.cn/cn/api/rate-limit)）。
- 主会话的请求为什么几乎不受影响，没有查明。

限流政策会变。审查又明显变慢时，按下节复测，不要凭印象改规则。

### 复测

只读查用量库的 `model_usage` 表，按 `first_token_at - started_at` 分桶，再按小时和「请求开始时同模型还有几个子代理请求在途」交叉。第 5 条的判定可以直接用（库的默认路径；被改过时见 `AGENTS.md` §5）：

```bash
python3 -B -c 'import os,sqlite3,time; s=sqlite3.connect("file:"+os.path.expanduser("~/.zcode/cli/db/db.sqlite")+"?mode=ro",uri=True); r=sorted((b-a)/1000 for a,b in s.execute("select started_at,first_token_at from model_usage where started_at>? and session_id like ? and model_id=? and status=? and first_token_at is not null",(int(time.time()*1000)-1800000,"sess_subagent%","<主会话当前模型>","completed"))); print(len(r),"条，中位",r[len(r)//2] if r else None)'
```

## 验收

- 复杂任务建议不超过六路，且明确服从更严格的当前上限。
- 既有审查维度和独立复核要求保持不变。
- 不满足「恢复同轮并发」的条件时，默认模型的审查员同一时刻只有一路在跑；`review-runner` 不超过 2 路，不承担判断类审查。
- 主 agent 的报告写明本轮用的节奏（逐路或同轮并发）和判定依据。
- `zcode-github-release` 的只读核查按同样的节奏派发：全量测试与静态检查、升级链解包、清单与正文的回读比对交给 `review-runner`，台账、冷文件与更新说明的核实留在默认模型的 subagent。
