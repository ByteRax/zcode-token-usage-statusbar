# 宿主卡顿治理（流式 / 空闲 / 数据链）

用户反馈安装本插件后 ZCode 卡顿。本规格只治理**计算与推送频率**，不改变任何展示口径、数值、文案和交互。

## 证据（2026-11-10；CDP 采样 + Precise Coverage + Node/Python 微基准；本机 2.5GB 库、1388 轮历史）

- 流式生成时，`turn-stats.js` 的 `ingest` 在**宿主 store 通知链内同步执行**，每次通知对窗口内全部文本做 `Array.from(text).length`（整串拆数组）：单次 0.35ms（20 行）→ 2.2ms（60 行 / 20k 流式字符）→ 4.1ms（60k），并产生大量 GC（采样里 GC 占主线程 12%）。
- `updateLive` 快路径在每次心跳（100ms）与每次 store 通知都调 `buildLiveTip`，整张 V2 速度 tooltip 串重新生成，**无人悬停也生成**；其中 `spdUnpack` 每次全量解包整张轮表：1400 轮 1.3ms、6000 轮 5.3ms（占生成成本 95%）。覆盖率计数：部署前 `buildLiveTip` ≈ 20 次/s、`spdNum` ≈ 22 万次/s。
- 历史（非 live）会话的 `updateLive` 每个心跳都落到整条 `render()`：急切构建全部 tooltip 串并跑五个 enhance*（单次约 8~20ms）。
- 轮播主开关默认关闭，但 65ms 定时器仍在做遗留 DOM 还原的两次整文档查询（~30 次/s）。
- Python 常驻泵每帧：命中帧 ~200ms、未命中帧 700~1100ms，**两者每 ~3s 交替**（TTL 2s < 泵间隔）。流式期间 `model_usage` 实际恒定不变（宿主请求完成才一次性 INSERT），重算纯属浪费；耗时大头是 `_project_usage`（~150ms×多键）、`_speed_history`（~150ms）、今日三查询与全库 scan。
- 宿主窗口被遮挡/隐藏（`visibilityState=hidden`）时 Chromium 把定时器降到 ≈1Hz、rAF 停发：此状态下的度量会把前台成本低估约一个数量级，度量前必须先核对可见性。
- **长会话的桥读取（issue #309，2026-11-12；读码 + 本机 CDP 只读 + 离线基准，报告者 Windows 实测另计）**：宿主 store 窗口不是固定尾部 60 行——本机真实宿主里 4 个轮次的会话 `rows.window` 就有 374 行，报告者 2289 轮会话为 6868 行。静态桥 v2 的 `getState()` 每次返回**整窗深拷贝并冻结**（`zuSnapshot`；本机 CDP 实测同一包装连读两次引用不同，`sameRefOnReread:false`），成本随窗口线性增长：本机真实宿主 374 行 ≈ 1.0ms；离线用真实 `zuSnapshot` + `turn-stats.js` 合成 6867 行，拷贝 16–61ms（随每行字段数）+ `ingest` 6–8ms；报告者 86.55ms/次。而 100ms 心跳里 `bridgeTick` 健康检查与 `updateLive → subRunningList` **每拍各读一次**（无 stats 时「思考中」合成再读一次），每次 store 通知还有 `subscribeStore.update` 与 overlay 回调各读一次——v2 桥下 ≥20 次整窗拷贝/秒，6868 行窗口主线程被占满（报告者 frameP50 120ms，长任务 96–172ms 几乎全是 `TimerHandler:setInterval`；关闭 `answer_rate_line` 使桥解绑后 13ms、0 长任务）。v3 桥（按底层引用缓存）让两次心跳读取变成命中，但 1.5.17 用户与「已热更 overlay、尚未重启客户端」的窗口期仍是 v2 桥，且通知路径每次状态变化仍有一次整窗拷贝，所以 overlay 侧必须**与桥代际无关**地去掉冗余读取并给通知路径封顶。
- **修复前后对照（离线，真实 `turn-stats.js` + 真实 v2 `zuSnapshot` 深拷贝 + 真实定时器与时钟；6867 行 / 2289 轮；脚本不入库，口径见下）**：按 overlay 的消费方式建模——旧=心跳每拍读 store 2 次、每次通知读 2 次；新=心跳读 handle 记录（2s 回源 1 次）、每次通知读 1 次并受规则 12 预算约束。 空闲（仅心跳）整窗读取 19.5→0.3 次/s、拷贝耗时 293→7 ms/s；5Hz 流式 33.8→3.8 次/s、467→67 ms/s；**10Hz 流式 48.8→4.0 次/s、677→68 ms/s（≈6.8%，落在规则 12 的 ≤~10% 上界内）**，事件循环最大延迟 84→26 ms。 注意 `mainThreadBusyPct` 含基准进程自身构造数据与 GC 的开销，绝对值偏高，只看相对变化。**度量陷阱**：overlay VM 夹具把 `performance.now` 换成不随真实耗时前进的假时钟，夹具内 `subscribeStore` 测得的处理耗时恒为 0，规则 12 的预算永不触发——在夹具里直接统计读取次数会得到“修后仍每通知一读”的假象；预算只能用注入时钟的单测（`turn-stats.test.cjs`）或真实时钟的基准验证。 **本机真实宿主上未做修复后的实测**（本机无已注册的大窗口流式会话；报告者 Windows 环境的修后数据待其反馈）。

- **issue #342（2026-11-15；报告者 Windows 10 22H2 / ZCode 3.18.2，zcode-lagfix 只读定时器归因 T1——只包宿主 `window.setTimeout/setInterval` 的 handler、只记录单次同步执行 ≥50ms 的回调，不改时机不读内容）**：1.5.19 在内置浏览器面板活动期间仍记录到 `bridgeTick` 51–93ms（原定 100ms）、`heavy` 55–75ms（600ms）、coordinator `tick` 54–63ms（600ms）、turn-stats `flush` 55–92ms（规则 12 合并批尾部处理）的单次慢拍；同一时段宿主帧 P95 103–303ms，T1 每 3 秒约 1–2 个慢拍。归因：规则 10–12 之后正常拍已 <5ms，慢拍是「正常 5–20ms 的工作在宿主主线程被 guest 长帧/GC 占用期间被拉长」与「长窗口会话 2s 回源一次的整窗深拷贝（报告者环境实测 ≈86ms/次）」两类；报告者场景是浏览器面板开在宿主窗口内（宿主窗口可见），`visibilityState` 门控对此无增益。guest 页面自身的 60–166ms interval 长帧不属本插件，报告者已另开 ZCode issue。
- **issue #452（2026-11-23；报告者 Windows 11 / ZCode 4.0.0.10870 / 1.12GB 库 / 千轮级会话，打字与滚动「不跟手」，剥离注入后消失；本机 ZCode 4.0.0 可见窗口 CDP 被动取证，不注入合成输入，窗口内宿主持续在改 DOM，约 3.4k 节点会话，默认主题内嵌形态）**：40 秒 `Tracing`（devtools.timeline）里 `track` 每帧被调 2400 次，FunctionCall 合计 3136ms（**均 1.31ms/帧、单次最大 25ms、占主线程墙钟 7.8%**）；嵌套其中的渲染工作合计占 89%——强制 `UpdateLayoutTree` 2227ms（2870 次，71%）、强制 `Layout` 497ms（462 次，16%）、PrePaint/命中测试/解析 68ms（2%）；样式重算与布局两项合计 87%；全线程样式重算时间 3022ms 中有 2227ms（74%）发生在 `track` 内。同窗口宿主自己的 rAF 回调 0.44ms/帧；浮层其余周期回调按各自节奏折算合计约 8ms/s、约占墙钟 0.8%（`bridgeTick` 0.33ms/拍、100ms 一拍；协调器 `tick` 1.2ms/拍、600ms；`heavy` 1.1ms/拍、600ms；两个 500ms 扫描各 0.25–0.31ms/拍）。**页内 A/B**（rAF 包装器让 `track` 循环暂停 8 秒再恢复，不动任何文件；两轮）：`RecalcStyleDuration` 均值 786→356ms/8s，LayoutCount 251→162，主线程任务时间均值 2024→1836ms/8s（约 −9%）。两组窗口的宿主 DOM 变更数不同（185/178 对 114/125），样式重算时间的降幅（430ms/8s）明显大于任务时间的降幅（188ms/8s），这部分差值没有被解释，不据此推算净收益；它又是「暂停循环」的近似，不是修复后版本的实测。**对报告者五条定位的核对结论**：①逐帧 `track` 成立，且是默认主题内嵌形态下渲染端的主因（高刷屏上 rAF 频率随刷新率升高、慢机器单次更贵；报告者环境的绝对占比未测，需其火焰图）；②100ms 心跳与④每帧推送在本机量级很小（本机 `speed_history` 1776 轮、帧比报告者的更大，推送处理在 profile 里排不上号，与报告者「`activity_min_ms` 调到 4000 无改善」一致）；③两个 500ms 扫描在 `answer_rate_line` 关闭时跳过报告者点名的重选择器全文档扫描（`scanRateLines` 在 `!state.rateLine` 处早退、`scanDeterministicLines` 在 `!state.rateLine || !TURN_STATS` 处早退），每拍仍各留一次轻量全文档查询（`scanPluginNotices` 的 `blockquote strong`、早退分支的 `[data-zusage-deterministic]`）；⑤`pillObserver` 仅药丸主题存在。**机制**：宿主每帧改 DOM（流式输出、打字、虚拟列表滚动）后，`track` 在同一帧的 rAF 回调里读几何，把样式重算与布局强制进本回调；而条内嵌在输入卡片里随卡片排版，这些逐帧读取只服务于显隐与溢出对账，不需要帧率。**范围边界**：药丸与 below-card 悬浮形态不在上述取证与修复范围内（门控对它们不设门，仍逐帧）；报告者原文把 `pillObserver` 列进打字场景，若其用的是这两类形态，v444 预期无改善。**真实 Chromium 隔离页冒烟**（无头 Chrome，仿宿主卡片夹具，旧 v440 与新 v444 同页对比；脚本不入库）：内嵌挂载、帧级补挂（21/22ms）、宿主隐藏输入区后的收条与复显（该夹具里由协调器回收并重建实例驱动，279/286ms、577/589ms）、窗口缩放跟随（0ms）、设置面板开合与定位逐项一致，`trackErr` 为空；窄宽档位自适应 128→275ms、回宽 252→294ms、原地改字 232→296ms（250ms 探针节奏叠加兜底节奏，增量不超过一个节奏）。合成页样式重算本身极廉价，旧新两版的重算次数相同，量不出真实宿主里的强制重算差值——差值只在上面的真机取证里成立。

## 产品规则（不变量）

> 编号约定：代码注释与测试里的「§N」指本节「产品规则 N」；验收场景用「验收 N」。

1. **展示不变**：tooltip 与统计行的数值与格式逐字不变；chip（速度格格面）的文案与结构见 [specs/speed-chip-stable-slot.md](speed-chip-stable-slot.md)（稳定占位批改为「标签+数值+单位」，统计数值与口径不变，tooltip 仍读真实视图）；悬停中 tooltip 仍 ≤100ms 跟手，打开瞬间内容必须是最新的（不得陈旧）。
2. **字符计数等价**：`ingest` 的字符数与原 `Array.from(text).length`（码点计数；高低代理对记 1，孤立代理项各记 1）逐值相同。
3. **轮表解包按引用缓存**：同一份 `speed_history` 对象重复 `spdUnpack` 只解包一次（WeakMap，随帧对象回收）；新帧是新对象自然失效；结果只读。
4. **未悬停不白建 tooltip**：实时速度 chip 所在格未悬停时，`updateLive` 不再每拍构建 tooltip 串，只记最新 view 并标失鲜（`__zuTipStale`）；`drawTip` 读取 `__tip` 前经 `liveTipRefresh` 补建；兜底每 1s 保鲜一次；悬停本格仍每拍构建并重画（v224 契约）；整条 `render` 重挂 `__tip` 时清失鲜标记。
5. **store 通知保持同步（廉价会话）**：store 驱动的 `updateLive` 在单次通知处理成本低时**不做合并/延迟**（曾试做 80ms 合并，测试与语义均依赖通知后同步更新状态条，已撤销；懒构建之后每次 `updateLive` 只剩微秒级工作，合并无必要）。**例外见规则 12**：该前提只对廉价会话成立——长会话每次通知含一次 O(window) 的桥拷贝与 `ingest`，仅当实测成本达到 `BUDGET_MIN_COST_MS` 才按成本自适应合并，其余会话行为逐字不变。
6. **空闲整条重渲染降频**：非 live 会话（`view` 为 null 且上一拍也非 live）且数据帧引用未变、距上次整条渲染不足 500ms 时，心跳不重复 `render`；数据帧变化、live↔非 live 切换、设置/主题变化（它们直接调 `render`）仍即时。
7. **轮播关闭态**：`rotatorCfg.enabled` 为假时，65ms 定时器的帧步降到 1s 一次（只剩遗留 DOM 还原）；开启或设置变更走 `rotatorMasterTick` 直调，不经此节流。
8. **model_usage 水位延长聚合缓存（Python）**：`_cached_agg`（scan / 今日三项）、`_cached_project`、`_speed_history_cached` 在 TTL(2s) 过期后，若水位 `(库身份, max(rowid))` 未变且距上次计算 <20s（`_WM_MAX_AGE_MS`），继续复用；水位一变（有新请求完成）立即重算。TTL 内行为不变；水位在**计算前**读取（计算期间的新写入只会使存下的水位偏旧→下次重算，安全方向）；内存库/桩连接/未带连接的调用取不到水位，退回纯 TTL。`_cached_agg` 保持 `(key, fn)` 二参签名，连接经 `_WmFn` 包装携带。
   **前提假设（宿主升级体检须复核）**：宿主只在请求结束时一次性插入终态行（completed/error/cancelled），不先写 `running` 再 UPDATE（宿主 `recordModelUsageFact` 与真库实测零 `running` 行）。水位对 in-place UPDATE、非尾行删除（含 session 级联删除）、尾行删除后 rowid 复用不可见——这些情形下陈旧上限即 `_WM_MAX_AGE_MS`；若宿主将来改成「先写 running 再 UPDATE」，「完成瞬间不陈旧」会退化为最多 20s。未加 `count(*)`：大表 O(n)（30 万行约 1ms，对比水位查询 ~7µs），且仍抓不到 in-place UPDATE。依赖 `session` 表的字段（会话名、项目名）与价表 12h 刷新带来的费用同样最长陈旧 20s，无 AGENTS 契约承诺它们实时。
   **降级结果**：`_speed_history_cached` 对空轮表（可能是 `session` 表读失败等降级的结果）不写水位，仍按 TTL 重试；`_today_detail` 内 `_scope_models_cost` 查询瞬时失败时的降级值（`cost: None`、`models: []`）目前不做同样处理——出现条件仅为瞬时失败（如库被锁），后果是今日费用/模型明细最长 20s 空白后自愈，与上述 20s 陈旧口径同类，已知并接受（不为此在签收后再改代码）。
9. 新增定时器/监听必须随实例 `dispose` 清理，热更新、导航、窗口关闭后停用（v328 批未新增定时器/监听；issue #309 批新增的条件性尾部定时器见规则 12）。
10. **心跳不读 store（issue #309）**：100ms 心跳路径（`bridgeTick` 健康检查、`updateLive` 内的 `subRunningList` 与「思考中」合成）不再直接调桥包装的 `getState()`，统一经 `handleSnapshot(h)` 读 handle 上的快照记录（`h.snap`/`h.snapAt`）。记录由通知回调写入（用 `subscribeStore` 传入的 state，零额外读取）；距上次更新超过 `SNAP_FRESH_MS`（2s）才回源 `getState()` 一次并回写——这次回源兼作 store 关闭/换代的探活（`getState()` 返回 null 或快照 `sessionId` 变 → 调用方按既有语义脱离重绑），探活延迟因此由 ≤0.1s 放宽到 ≤2s（`v88` 以前本就是 2s 心跳）；pane 切会话仍由 `handle.sid`/`sideKey` 与当前会话的比对**即时**重绑，不依赖探活。展示不变：宿主每次状态变更必通知（v3 桥缓存也以通知为失效点），记录与逐拍读取同样新鲜。与桥代际无关，v2/v3 均有效。
11. **每次通知只读一次**：`subscribeStore` 把本次已读的 state 作为参数传给 `changed(state)`，overlay 回调直接使用，不再二次 `getState()`（v2 桥下每读一次 = 一份整窗拷贝）。
12. **通知处理预算（仅对昂贵会话生效）**：`subscribeStore` 记录上一次通知处理（读 store + `ingest` + `changed`）的实测耗时 `cost`。`cost < BUDGET_MIN_COST_MS`（8ms）时行为与此前完全一致（每次通知同步处理）；`cost ≥ 8ms` 时，距上次处理结束不足 `min(BUDGET_MAX_GAP_MS(1000), cost × BUDGET_GAP_RATIO(9))` 的通知**合并**：只置 `pending`，并保证一个尾部 `setTimeout` 在间隔届满时处理**最新**状态（中间快照既不读也不 `ingest`；`ingest` 以 `seq` 单调，丢中间帧无副作用）。上界：插件通知处理占主线程 ≤ ~10%（`cost / (cost × (1 + 9))`），最长陈旧 ≤ 1s。尾部定时器归该订阅持有，`off()` 时清除，订阅关闭后即使已排队也不执行；`unref` 以免挂起 Node 测试进程。**已知后果**：昂贵会话（窗口 ≳ 2000 行）的实时 t/s 刷新由逐通知降为 ≤ ~1Hz；短于一个合并间隔（≤1s）就完成的轮次可能没被「实时观察到」（`observedLive=false`），按重绑时捞到已完成历史轮的既有口径处理（overlay-bridge 测试 ⑯/⑰）。一次性的 GC/JIT 尖峰可能让紧随其后的一次通知多等 ≤~0.3s，下一次处理测得小成本即恢复。
   **复审补充（A/E 两路独立审查）**：①丢中间帧对 `observedLive` **不严格无副作用**：昂贵会话里若某轮在一个合并间隔内开始并结束（命令秒回），尾部处理只看到已完成态，`seenIncomplete=false`，历史行可能显示「本轮统计不可用」；概率低（LLM 往返通常 >1s，且仅长会话触发），按已知取舍接受。②合并后每次处理后紧接的一次实时读数偏低（模拟：起步 1~2s 约 −30%，稳态约 −5%~−10%），`characterRate` 的 2s 窗口与 200ms 下限在 ≤1s 间隔下仍成立，常量不调。③子代理槽位回调同样遵守规则 11（v341）；同步处理分支会作废迟到的尾部定时器；全局 `setTimeout`/`clearTimeout` 缺席时 `arm` 失败退回同步处理，不留无人冲刷的 `pending`。④宿主 `snapshotTailWindowRows:60` 只截 wire/hydrate 快照，渲染端 reducer 增量只增不截（源码核对）——窗口可达数千行。

13. **会话级聚合按 (库身份, sid) 缓存**：`session_usage`、`_session_snapshot` 的会话均速（`sess_avg`，全会话 `fetchall` 后逐行 `_turn_rate`）与耗时均值（`sess_av`）改由 `_cached_session(con, sid, kind, fn)` 承载，键为 `(库身份, sid, kind)`，与 `_cached_project` 同款 2s TTL + 水位续用（上限 20s），超过 32 条时整表清空、只损失缓存（写入前判断，峰值至多 33 条）。**实测效果与边界（合成库基准，同机前后对比）**：只改善**命中帧**（5.6 万行/主会话 8,237 行：189→130ms，约 −31%）；**对「每帧都有新请求完成」的 miss 帧几乎无效**（842→847ms），因为水位是全库 `max(rowid)`，任何新写入都使全部会话键失配。**真库复测**（本机 2.7GB 库，`model_usage` 69,496 行、最重主会话 1,415 行；只读；旧版=HEAD，新版=运行目录部署版）：命中帧仅 −9%～−14%（140→121ms、162→148ms）——远小于合成库，因为真库最重会话只有 1,415 行；冷帧不变（1035→1049ms、1109→1104ms）；`_sub_agent_tasks` 冷扫描仅 33ms（5,538 个 part 行），规则 15 在该数据上收益很小，价值取决于 part 体量。真库冷帧热点（cProfile 占比）：项目聚合 `_cached_project` 57%（`_project_usage`×N 36% + `_all_projects_usage` 22%）、`_speed_history` 20%、会话级 `_session_snapshot` 12%，与合成库一致，根治目标是前两项。此前把「长会话行数」当主因是误判：基准里主会话 8,237→30,000 行时 miss 帧基本不变（6.6s→5.9s），而全库行数 5.6 万→36.8 万使 miss 帧涨 7.8 倍（0.84s→6.6s）——**帧成本随全库总行数线性增长，与单会话行数几乎无关**，主要热点是全库扫描（`_speed_turns` 约 31%、`_project_usage`+`_all_projects_usage` 约 42%）。根治需增量聚合（后续独立立项，见「未做」）。**降级**：内存库/桩连接取不到库身份时退回每次真算（不共享缓存；`_db_cache_key` 对桩连接的 `AttributeError`/`TypeError` 同样降级为 `None`）；`session_usage` 返回值经浅拷贝出缓存，调用方改动不污染缓存。**口径提示（review 发现，有意接受）**：缓存是进程级的——常驻 `serve` 与同进程多次调用的 `usage_mcp.py` 内，同一会话在 2s TTL 内读到的 `session_usage`（含经它的 `render_current` / `render_session_detail`）可能是调用前的值，水位变化后 TTL 一过即重算；一次性 CLI 每次新进程不受影响。与既有 `_scan_session_ids` 的 2s 缓存同口径，不改 stdout 契约、不加字段。
14. **`_provider_fallback` 挂缓存**：全表 `order by completed_at desc limit 1` 每帧必跑，改为 `_cached_agg` 覆盖（键 `provfbk`，2s TTL + 水位），返回空串时同样缓存（空值是稳定结果，不重复扫表）。**`_AGG_CACHE` 键清单与容量（review 实测）**：稳态 5 个键（v375 前：`scan` / `provfbk` / `today` / `todayrate` / `todaydetail`）；**v375 起 `todayrate` 并入 `todaydetail`（值含 tps/models/cost），稳态 4 个键**（`scan` / `provfbk` / `today` / `todaydetail`）；`_cached_agg` 在**写入前**判断 `len > 8`，故最多容纳 9 个键、写入第 10 个键时才整体清空（实测：第 9 个键照常写入，第 10 个触发清空）。一次跨自然日时 v375 前三个 today 键各多一份、峰值 8 余量 1；v375 起两个 today 键各多一份、峰值 6 余量 3；旧日键没有淘汰路径、只能靠整体清空回收，常驻进程活过第二次跨日会清空一次（实测：先到 9，再回落；只丢缓存、自愈）；库文件身份变化时再多一个 `provfbk`，峰值 9、不清空，余量归零。**新增 `_cached_agg` 键前必须核对并上调该容量**，否则会周期性清空 v328 的热条目。容量被 v328 的 `assertLessEqual(len(zusage._AGG_CACHE), 9)` 钉住（`test_cache_dicts_stay_bounded` 与 `test_watermark_dicts_never_keep_orphans_when_caches_overflow` 两处），调大须同步改这两个断言（两个用例分别写 20 个和 12 个键，容量调到不同幅度时先红的用例不同）。本 PR（含 v375 合并 todayrate）未上调：v375 后余量 3 个键，更不值得动既有守卫。
15. **part 正文扫描热路径最小重扫间隔**：`_sub_agent_tasks` 的 `part.data LIKE` 扫描（流式期间 part 持续新增、失效键每帧失配）在快照热路径经 `_sub_agent_tasks_hot(con, sid)` 调用，最小重扫间隔 3000ms（`_TASK_RESCAN_MS`）：键失配但距上次计算不足该间隔时复用上次结果（子代理任务名最长陈旧 3s，展示层可接受）。CLI 文本报表仍走 `_sub_agent_tasks` 精确路径，不受影响。
16. **查询泵慢帧冷却（冷文件）**：`inject-main.cjs` 在 `done()` 结算处记录上一帧实耗 `lastQueryMs`（封顶 15s）与结算时刻 `lastDoneAt`。**限频原本只从「发起」起算**：帧耗时 ≥ `activity_min_ms` 时，结算瞬间间隔早已满，下一帧零间隔紧接发出，serve 连续执行、占空比 ≈100%（离线探针 60s/帧耗 6s 实测）。现增加**冷却从结算起算**：结算后须再等 ≥ `lastQueryMs` 才放行，占空比 = T/(T+T) ≤ 50%。**冷却对所有帧生效，不设「T > 有效间隔」门槛**：首版曾带该门槛，真库实测（本机 2.7GB / 69,496 行）冷帧约 1.05s，低于 `activity_min_ms`(1.5s)，冷却根本不介入，占空比仍约 68%（T=1.2s 时 77%、T=1.4s 时 90%），且在 T 跨过间隔处从 ~100% 骤降到 50%（不连续）。无门槛后离线驱动实测（`activity_min_ms=1500`）：T=1050ms→47%、1200ms→50%、1400ms→49%、6000ms→50%；T ≤ 间隔/2（750ms）时旧限频门（发起+间隔）已比冷却（结算+T = 发起+2T）更严，节奏与旧版逐字一致（T=600ms 周期仍 ~1.43s）。**代价**：T > 间隔/2 的重负载下计数类数字刷新周期由 ~1.5s 变为 ~2T（本机冷帧约 2.1s）；`activity_min_ms` 仍是下限。**已知副作用（远端/混合帧，有意接受）**：T 取挂钟耗时，远端帧含 ssh 往返，而这段等待并不占本机 CPU，冷却对它偏保守。远端帧结算后原本就有 `scheduleRetry(remotePollMs())`，冷却只在 `lastQueryMs > poll_ms`（缺省 3s，下限 1s）时才比它更晚：结算→下一帧由 `poll_ms` 变为 `T`，整周期由 `T+poll_ms` 变为 `2T`（T=5s 时 8s→10s）；T ≤ `poll_ms` 的远端帧不受影响。不按「是否含远端 scope」豁免，是因为「本机大库 + 远端分栏并存」时本机那部分仍要受保护，而豁免会让这类用户整体失去保护。**真机核验（本机 2.7GB 库，重启后只 `touch` 库 mtime 触发泵、采样 serve CPU，42s/26 帧）**：轻帧（CPU ≈0.18s）周期中位 1.53s，与旧节奏一致；两个重帧（CPU 1.07s/1.11s，对应启动首帧与 `_WM_MAX_AGE_MS` 20s 兜底重算）之后下一帧的起点分别晚 2.10s/2.46s（旧门只会给 ~1.55s），符合 `2T+50ms`；该负载下 serve 单核占用约 16%。此证据只证明门在真实泵里生效，不代表报告者环境（其帧耗时与写入频率未知）。常驻进程单请求超时同步改为 `max(15000, 2 × lastQueryMs)`（`lastQueryMs` 封顶 15s，故**上限实为 30s**；曾写作 `min(45000, …)`，45s 上界永远到不了，已删除），防止合法慢帧被 15s 硬杀、丢缓存冷启动。首帧/零耗时两式均退回原值。**审查后有意不改（review 第 1 轮）**：①超时被硬杀的帧同样按实耗（封顶 15s）记入冷却——无法区分「仍在重计算」与「进程挂住」，而杀后常驻进程冷启动、缓存全丢、下一帧更重；**这一记录同时是超时放宽的前提**：`lastQueryMs` 决定下一帧超时 `max(15s, 2×)`，若对被杀帧清零，15–30s 之间的慢帧永远等不到放宽后的超时而被反复杀死（离线驱动实测，窗口 600s、帧恒 20s：当前 16 帧完成、周期约 35s（20s 帧 + 15s 冷却）；清零则 0 帧完成、39 次被杀、周期约 15s，请求几乎一直在途），勿「好心」改回。重计算场景下常驻进程墙钟占用由约 100%（旧版 15s 超时加零间隔重连）降至约 67%（30s 超时 + 15s 冷却；属墙钟占比，进程挂住时 CPU 并不满）；重复挂住时单次恢复最长多等约 30s（超时由 15s 放宽到 30s，再加 15s 冷却）；②系统时钟回拨：新冷却门与既有限频门（`now - lastSpawn`）都会停滞到时钟追上，既有门本就停滞，单改冷却门在端到端不可观察，故保持一致、不单独处理（`done()` 的 `spent >= 0` 守卫同理）；③冷却对所有帧生效，用户把 `activity_min_ms` 调到 300 想更跟手时，T > 150ms 的帧周期仍约 2T——本规则已声明的取舍。

18. **回源退避与周期对账自适应降频（v349，issue #342）**：两处与桥代际无关的热路径缓释，只在实测单拍成本超预算时介入，廉价环境逐字不变。
    a. **`handleSnapshot` 回源退避**：规则 10 的陈旧回源（>2s 回源 `getState()` 一次并兼作探活）记录本次实测耗时（`perfMs()` 差值，`performance.now` 优先、缺位回退 `Date.now`）；≥ `SNAP_SRC_BUDGET_MS`（8ms，与规则 12 同阈值）时该 handle 的新鲜窗按 2 的幂退避 `SNAP_FRESH_MS × 2^mul`（2s→4s→8s 封顶，`mul ∈ {0,1,2}` 挂 handle）；< 8ms 立即回 1 档——新会话/小窗口会话自动恢复 2s。影响面只有静默期两类数据的陈旧上限由 ≤2s 放宽到 ≤8s：store 静默期继续合成「思考中」所依据的 phase 快照、与 backgroundWorks 补给清单（「已观察 Xs」走字按 `bornAt` 每 100ms 心跳推进，不受退避影响），且仅发生在回源本已 ≥8ms 的长窗口会话；活跃期快照由通知回调写入（宿主每次状态变更必通知），回源本就不发生；pane 切会话仍即时重绑、不经探活。报告者环境 86ms 深拷贝的频率由每 2s 一次降至每 8s 一次（占空比 4.3%→1.1%）。
    b. **heavy/coordinator 600ms 对账自适应降频**：两处 `setInterval(…, 600)` 的定时器拓扑与 dispose 语义不变；体内以 `perfMs()` 计时，单拍同步 ≥ `TICK_BUDGET_MS`（16ms，一帧预算，含界）时升档（`lvl ∈ {0..3}`，每次实跑升一档后封顶），跳过距上拍实跑不足 `600ms × lvl` 的触发（窗口右开：恰 `600ms × lvl` 不跳），< 16ms 立即回 0 档。setInterval 不提前触发，稳态下相邻触发恰隔 600ms：lvl=1 稳态不产生跳拍（只吸收「前拍被宿主拉长、后拍准点回位」的尖峰形态——恰是报告者环境），稳态有效降频自 lvl=2（1.2s）起、封顶 lvl=3 → 有效间隔 1.8s。语义：只在单拍已被实测拉长（宿主主线程被 guest 长帧/GC 占用，含任务排队造成的墙钟拉长）时降低对账频率让出主线程；降频期最坏影响是 chip 丢失兜回、pane 消失条自藏、会话切换渲染延迟至 ≤1.8s——只发生在本已卡顿的环境。健康机器（单拍 <16ms）行为逐字不变。 差值为负（系统时钟回拨）一律视为到期、不冻结对账，规则 19 的空闲门同此口径。
    c. **诊断（供报告者环境归因）**：`window.__zusageDiag` 新增 `snapSrcMs`（上次回源实测耗时）、`heavyCost`、`coordCost`（上次对应 tick 实测耗时），随主进程既有 ~15 泵 diag-`<n>`.json 落盘；只加数值字段，不改任何既有字段。
    d. **有意不做**：bridgeTick 100ms 心跳不降频——规则 1 悬停 ≤100ms 跟手与「思考中」走字钉住该节奏，其慢拍主因由 18a（回源）与规则 6（空闲整条渲染 500ms 节流）覆盖；`flush`（规则 12 合并批尾部处理）已有 ≤~10% 占空比上界、成本即合并批自身，不再叠加；`document.visibilityState` 门控不加——Chromium 对隐藏窗口本就把定时器降到 ≈1Hz（证据节），且报告者场景宿主窗口可见，门控无增益。

    - **下一帧立即执行**：有脏标 `trackDirty`——`render()` 重建条面后（切档 `applyBarTheme()` 尾部同走 `render`）、`dedupBars()` 解除让位抑制后置位；条面 `main` 横向滚动后（监听只置脏标、不读几何，经 `listenGlobal` 挂在条内 `main` 上随实例销毁；`zu-clip`/`zu-clip-left` 渐隐提示因此仍是下一帧跟随）；`cardMode` 自上次几何段以来翻转（悬浮与内嵌互切后的首帧）；`innerWidth`/`innerHeight` 较上一帧变化（每帧两次标量比较，不触发布局，同时进入保持期）。
    - **兜底对账**：以上都不成立时，距上次几何段不足 `TRACK_IDLE_MS`（100ms）的帧直接返回（差值为负的系统时钟回拨一律视为到期，与规则 18b 同口径，不冻结对账；回拨同时把保持期截止时刻 `trackFastUntil` 作废——它只在视口变化时写入，时钟被校正到过去之后会落在「未来」，不作废则门被撑开、逐帧执行到时钟追上；作废先于视口判断，回拨与视口变化落在同一帧时本帧的视口变化照常重新武装保持期）。宿主自发的布局变化（侧栏折叠、终端面板开合、模态弹窗、幽灵壳）没有插件侧事件，由该节奏兜住：溢出与折叠对账最多晚一个节奏（条内原地改字引起的宽度变化同此）；收条判定叠加 150ms 可见缓存后最多晚约两拍才被发现，既有 400ms 迟滞再按拍量化，合计相对逐帧最多晚约 200ms（验收用例的时间线即 +100 命中缓存、+200 判被盖、+700 收条）。
    - **不做的事**：不新增定时器或观察器，只新增上述一个条面 `scroll` 监听；不改几何段内部任何读取与判定；`hideSince` 迟滞、窄宽 250ms 探针、5 秒 mount 诊断都在几何段内、随几何段执行（节拍只会变粗）；不动 100ms 心跳、600ms 对账与两个 500ms 扫描。
    - **诊断**：`__zusageDiag.mount` 追加数值字段 `trackFrames`、`trackPasses`（实例生命周期内走到门的帧数、执行几何段的次数，随既有 5 秒 mount 诊断落盘），只加字段不改既有字段，供报告者环境核对门控生效（空闲内嵌态 60Hz 下比值约 1/6）。读数边界：超限气泡显示期间 `syncExcBubble` 在门之前逐帧读两个矩形（既有行为，门控对它无收益，此时比值仍约 1/6）；精简主题分支的 mount 诊断不带这两个字段；多分栏时只有 0 号实例写，0 号不是内嵌形态时比值不代表其它实例。
    - **有意不做（issue #452 另三条建议）**：`speed_history` 指纹去重推送仍列「未做」（冷文件加主桥到渲染端的协议改动，本机实测推送处理在 profile 里排不上号，不是卡顿主因）；两个 500ms 扫描的范围收敛不做（关闭态已跳过重选择器扫描、只剩每拍一次轻量查询，开启态 0.25–0.31ms/拍）；大库冷帧的增量聚合见「未做」的既有立项，持久化缓存未立项。

## 验收场景

1. `ingest` 对含 emoji、孤立代理项、中英混排的文本得到与 `Array.from` 相同的字符数；同一行文本未变时命中缓存；文本变化时重算；行移出窗口后缓存释放；热路径不再对字符串调用 `Array.from`（变异：换回旧实现该守卫测试变红）。
2. `updateLive` 快路径：未悬停且距上次构建 <1s → 不调 `buildLiveTip`、`__tip` 标记失鲜；满 1s 保鲜；悬停本格 → 每拍构建并重画；`drawTip` 读取失鲜格前先补建（顺序锁）；补建异常不外溢。
3. `spdUnpack` 同一 `speed_history` 引用重复调用只解包一次；新引用/轮数变化重算；结果与未缓存实现逐字段一致。
4. 空闲会话：同一数据帧下 500ms 内的心跳不 `render`；数据帧引用变化即渲染；满 500ms 兜底渲染；live→非 live 切换即渲染；view 非空的结构切换不受节流。
5. 轮播关闭态帧步按 1s 节流；开启后恢复 65ms 节奏。
6. 水位缓存：TTL 过期且水位未变 → 复用；新请求完成（水位变）→ 立即重算；超过 `_WM_MAX_AGE_MS` → 兜底重算；TTL 内不碰库；内存库/无连接纯 TTL；计算期间并发写入强制下一帧重算（变异：把水位读取挪到计算之后/让水位缓存恒失效，对应测试变红）；缓存字典有界。
7. 真库对比（只读，隔离 HOME，同一请求 1.5s 节奏）：旧版逐帧 190↔900ms 交替（均值 474ms），新版稳定 ~200ms、仅每 20s 兜底重算一次（均值 268ms）。
8. 根产物 `overlay.js` / `turn-stats.js` / `zusage.py` 与 ZCode 插件副本、WorkBuddy 插件副本一致；`python3 sync_plugin.py --check`、`scripts/sync_workbuddy_plugin.py --check` 通过。
9. **心跳读次数（规则 10）**：绑定后连续 N 个心跳（无推送、记录新鲜）→ `getState` 调用 0 次；记录陈旧（>`SNAP_FRESH_MS`）后的首个心跳回源恰好 1 次并刷新记录，之后又回到 0 次；陈旧后 store 已失效（`getState` → null）→ 该心跳即脱离并重绑到替换 store；pane 切会话不等探活、同一心跳即重绑（变异：把 `handleSnapshot` 换回直接 `getState()` 或让记录恒新鲜，对应测试变红）。用「每次读都是整窗拷贝」的计数桩复现症状路径，不依赖计时。
10. **每通知读一次（规则 11）**：一次 store 推送使 overlay 路径总计只调 1 次 `getState`（含 `updateLive` 内 `subRunningList`/「思考中」合成）；`subscribeStore` 把读到的同一 state 对象传给 `changed`。
11. **预算（规则 12）**：廉价（`cost < 8ms`）→ 连发 N 次通知同步处理 N 次；昂贵 → 间隔内通知合并为一次尾部处理、尾部处理的是最新状态、只排一个定时器、间隔届满后的下一次通知恢复同步；`off()` 清定时器且已排队的不执行；`dispose` 后 `timers.size === 0`；尾部处理中 `getState` 抛错不外溢；`cost` 恰为阈值 / 间隔恰为上界的边界值各有用例。

12. **轮播附加工作时长（规则 17）**：同一秒内连续 masterTick → `.zu-rotator-elapsed` 的 textContent 与行容器的 data-tip 写计数为 0（label/行上非本功能的既有无条件调用除外，如 slot 标记与 active 类）；秒值跨变后的首个 tick → 恰各 1 次写；`document.querySelectorAll` 调用计数相对基线不增；关闭 appendWorkDuration 或 labelSource=host → span 摘除且恢复路径无新增查询；主开关关闭态 1s 节流行为不变（规则 7 复验）。v443 实时速度段同预算验收：内层档位 span 同值/同秒零写、跨值每行 1 写/秒（advanceNow(1000) 后恰好补写一次）、零文档级查询增量。

13. **回源退避与对账降频（规则 18）**：
    - **18a**：注入「`getState` 时使假 `performance.now` 恰前进 8ms」的读取桩（≥ 阈值含界，`>8` 变异红）——陈旧回源后 2.5s 内的心跳不再回源（退避生效，读取计数不变），满 4s 恰好再回源一次；第三次贵回源断言新鲜窗停在 8s（封顶，`min(2→3)` 变异红）；换回零成本 `getState`（<8ms）后 8s 窗届满回源、档位回落，此后 2s 即回源（变异：去掉退避，第一段断言变红）。廉价桩（成本 <8ms）下回源节奏仍为 2s（既有验收 9 用例复验通过）。
    - **18b**：heavy/coordinator 各以「每次实跑恰 +16ms」的标记桩注入成本（`>16` 变异红）——降频窗口内的拍被跳过（body 副作用不发生：compact 条不补挂 / 消失 pane 的实例不 dispose）；恰 `600ms` 不跳拍（窗口右开，`<→<=` 变异红）；连续贵拍把档位推到 3 封顶、越过 `600×3` 窗界的触发必须执行（`min(3→4)` 变异红）；恢复廉价后档位回落、600ms 节奏照旧（变异：去掉跳拍门，跳过断言变红）。降频门不改变定时器拓扑：dispose 后 `timers` 清零等既有用例不变。
    - **18c**：各测点写入 `snapSrcMs/heavyCost/coordCost` 数值字段（恰等于阈值可断言）；`perfMs` 的 performance 缺位/`now` 非函数两形态回退支有独立单测；既有 `__zusageDiag` 字段与 diag 落盘节奏不变。
14. **`track` 空闲门（规则 19；`overlay-lifecycle` 夹具：复用 issue #342 的 `fakeClock`，新增 `Element.cloneNode()`（窄宽探针）并把夹具 `Element` 类暴露给 VM 沙箱，`runFrame` 改为「取走队列再执行」的真实浏览器语义——旧实现重跑历史回调，track 自调度按 2^帧数 复利增长；全部用例在首帧之前冻结时钟）**：内嵌形态首帧执行几何段后，时钟不动连跑 N 帧，composer 的 `getBoundingClientRect` 调用数不增，条被清掉后的下一帧仍补挂回卡且不读几何（变异：去掉门控或把 `TRACK_IDLE_MS` 改 0，变红）；时钟前进 99ms 不执行、恰满 `TRACK_IDLE_MS` 的下一帧执行一次；时钟回拨（差值为负）当帧执行，视口变化之后再回拨同样只执行一次、随后的空闲帧不读几何（删回拨作废保持期变红），回拨与视口变化落在同一帧时保持期照常武装（作废挪到视口判断之后变红），回拨落在脏标帧（条面重建）时同样作废（作废加了「仅无脏标」条件变红）；`render()` 之后下一帧立即执行且只执行一次（切档尾部同走 `render`）；⚙ 设置面板、⋯ 菜单（narrow 档）、子代理浮层任一打开期间每帧执行，关闭后回空闲；`innerWidth` 与 `innerHeight` 各自单独变化都当帧执行、基线回写（变化消化后保持期外回空闲，删高度基线回写变红），保持期内（含不足 100ms 的帧）逐帧执行、恰满保持期回空闲（仅高度变化后的保持期同样逐帧，改成只在宽度变化时武装变红）；条面 `scroll` 后下一帧执行且只执行一次；无工具行的 below-card 形态每帧执行；`cardMode` 由假翻真后的首帧执行；宿主遮挡输入框（无插件侧事件）由兜底节奏在迟滞期满后收条、解除后复显；`dedupBars` 解除抑制后的下一帧复显（v177 与 v408 面板去重两个用例，断言帧前推进假时钟让几何段真的执行，并断言该帧确实读了几何——推进量与节奏常量恰好相等、余量为 0，常量一改要大声变红；读取计数会被另一实例的命中判定读到，两个用例另以「对手退场后不推进时钟的下一帧由实例 b 复显」证明实例 b 自己的几何段在跑）；收条迟滞按 100ms 网格断言「首个被盖帧不立即收、迟滞恰 400ms 仍不收、期满收条」，并以第二个遮挡周期守住复显时的迟滞计时复位（`> 400` 改 `>= 0`/`>= 400`/`> 300`/`> 500`、删 `hideSince = 0` 各自变红）；mount 诊断的 `trackFrames`/`trackPasses` 断言精确值（首帧 + 30 个空闲帧 + 本次 = 32 帧、2 次几何段）；每个新用例收尾断言 `__zusageDiag.trackErr` 为空。**夹具沙箱须暴露 `Element`**：缺它时首个「被盖」帧在 `diagHidden` 的 `el instanceof Element` 处抛 ReferenceError、被 track 外层 catch 吞掉，迟滞计时根本不起而用例照样通过（v444 review 实证）。

## 未做（已评估，留作后续）

- 渲染端：`track()` 几何读取在卡片内嵌形态已按规则 19 门控（v444）；药丸与 below-card 悬浮形态仍逐帧（条不随卡片排版，需逐帧跟随），再降须先给悬浮形态找到不读几何的跟随手段。`hcObserver`/quota observer 缩小观察范围（依赖 Radix portal 假设，需先验证）；`heavy` 与协调器 tick 的双倍频率（本机 1.1–1.2ms/拍）。后两项前台实测前不动。

- **大库 miss 帧根治（后续独立立项，需先改规则 8 的陈旧界语义）**：帧成本随**全库总行数**线性增长（合成基准：5.6 万行 miss 帧 0.84s → 36.8 万行 6.6s），热点是 `_speed_turns`（全表 GROUP BY×2，约 31%）、`_project_usage`×N + `_all_projects_usage`（约 42%）；规则 13–16 只能把占空比封顶到 ~50%、改善命中帧，**不降低 miss 帧本身**。方向：宿主「只 INSERT 不 UPDATE」（规则 8 前提）使按 `rowid` 水位增量聚合可行——仅扫 `rowid > 上次水位` 的新增行并并入既有聚合，低频全量对账兜底。代价：`in-place UPDATE`/非尾行删除的可见延迟从 ≤20s 变为对账周期；须配套对账用例与「增量结果 ≡ 全量重算」的等价性测试。
