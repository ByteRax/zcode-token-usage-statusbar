# 渠道分支精简与重建对账

## 目标与边界

- 渠道分支 `plugin-releases` 与 `plugin-releases-gitcode` 只承载渠道清单 `marketplace.json`（外加 `LICENSE`），不再携带源码树。宿主用 git 克隆维护市场来源并按快进跟进 ref（issue #497 的克隆 reflog 实证；「刷新按 ref 下载归档」的旧假设与该证据矛盾，勿再据此推断断链无害），整树分支让每次更新检查多下载与安装无关的内容。
- 清单的内容、身份与校验语义不变：仍是 `build` 输出的 `marketplace-release*.json`，仍指向正式 Release 的 ZIP 与它的 sha256。
- 补推（Release 已发、渠道清单未更新）时的对账从「字节相同」放宽到「内容相同」。发布包的字节可能随打包机与压缩实现变化，内容不变才是对账要守的不变量；渠道清单里的 sha256 必须是线上资产的摘要，不是重建产物的摘要。
- `build` 用 DEFLATE（级别 9）打包，文件集与成员内容不变。此前成员不压缩，整包约 4MB，其中绝大部分是可压缩的脚本与文本。
- 工具只生成提交对象与清单文件，不推送、不动工作区。快进推送属于发布技能的阶段 E，授权范围以该技能为准。换精简分支与之后的每次发版都是同一条快进链（以远端旧提交为 parent 重建树提交后普通推送），全程不需要强推；孤儿提交只用于首次创建全新分支（issue #497：孤儿 tip 断开快进链，市场克隆会静默卡在旧清单——2026-11-26 实际发生，见该 issue）。

## 规则

- `release_tool.py reconcile`：重建包与线上包各自通过 `verify`，仓库、版本、tag、插件身份与资产名一致；字节相同直接通过；字节不同则逐成员比对名称与内容，任一成员不同即失败。通过后把渠道清单写到 `--catalog-out`，清单以线上发布包内的 `marketplace.json` 为底，`source.sha256` 取线上发布清单的值。
- `release_tool.py channel-commit`：读入渠道清单，校验插件名、版本与资产的 sha256、URL 形态；生成只含 `marketplace.json` 与 `LICENSE` 的提交对象并输出提交哈希。已有分支必须给 `--parent`（缺省拒绝生成提交，报错指引传 `--parent`；消费者按快进拉取，孤儿 tip 会让它们静默卡在旧清单，issue #497）；`--orphan` 生成无父提交，仅限首次创建分支。
- 存量渠道分支换成精简分支：先确认远端原清单的版本不高于新清单，再以远端旧提交为 `--parent` 重建树提交，普通快进推送即可（提交层面是快进，树从整树变精简树不影响）；不需要强推。「孤儿提交 + 强推」的换法已废弃（issue #497）。之后的每次发版同样用 `--parent` 做快进推送。

## 验收

| 场景 | 可观察结果 |
|---|---|
| 重建包与线上包字节相同 | 对账通过，清单的 sha256 等于线上资产摘要 |
| 重建包与线上包字节不同、逐成员内容相同 | 对账通过并注明不是字节相同，清单的 sha256 仍等于线上资产摘要 |
| 重建包任一成员内容不同，或版本、仓库不一致 | 对账失败，不写出清单 |
| 渠道清单的版本或资产形态不合法 | 不生成提交 |
| 不给 `--parent` 也不给 `--orphan` | 拒绝生成提交，报错指引传 `--parent`（或首次建分支用 `--orphan`），不留任何对象 |
| 给 `--orphan` | 生成没有父提交的提交，树里恰好是 `marketplace.json` 与 `LICENSE`（仅限首次创建分支） |
| 给 `--parent` | 生成以它为唯一父提交的提交 |
| 任意一次 `channel-commit` | 工作区与索引没有变化，没有任何推送 |

自动化验收使用 `tests/test_release_tool.py`；线上渠道分支的实际替换需维护者按发布技能授权执行。
