# 项目健康巡检与优化交接

## 目标与边界

新增仓库维护技能 `zcode-health-review`，持续发现有证据的质量退化与高价值改进机会，由 `zcode-prd-to-spec` 承接选定问题的方案和实现。技能位于 `.zcode/skills/`，不属于插件分发文件，不安装到全局技能目录，不建立定时任务。

巡检成功不以问题数、改动量或拆分文件数衡量。没有值得修改的问题可以正常结束；未检查的领域不应被描述为健康。

## 权限与状态所有者

- 用户决定范围和操作权限。扫描深度（日常、专项、全面）与动作权限（只读巡检、仅出方案、实施）独立；全面扫描不代表允许修改。
- 巡检技能负责基线、覆盖范围、证据分级、去重和问题筛选，不直接承担安装或发布流程。
- 方案技能复核交接证据，决定修复、优化、暂缓或不处理；没有实现授权时只输出方案。明确授权实施时，不再逐项重复询问已确定的范围。
- 主会话负责方案取舍、修改和最终验证。子代理可按宿主与项目策略承担独立只读核查；技能间交接是同一任务中的职责切换，不隐含新建或发送消息到其他会话。
- 只读巡检默认在对话输出，不创建报告、spec 或台账文件。仅在用户明确要求保存或本轮已有明确写入授权时，更新指定的项目本地台账；不写个人记忆，不提交，不上传敏感信息。

## 基线与问题契约

- 首次运行没有历史基线时，建立当前检出的模块概览和风险抽样；不把当前发现直接称为新增回归。后续优先检查可信基线以来的变化及其上下游，并轮换复查未覆盖或较久未检查的领域。
- 基线包含检出身份、HEAD、相关工作区差异和实际覆盖范围；仅记 HEAD 不能识别未提交变化。基线不可比较或途中发生并行修改时，标明失效范围，重新取证或停止受影响检查，不推进该领域的可信覆盖记录。
- 同一问题按模块、契约和根因识别，不能只用行号或标题去重。既有接受风险必须有用户决定；条件变化时重新评估，不能自动永久忽略。
- 问题交接至少包含编号、触发条件、证据、影响、已知与未知、处理建议、兼容约束、验收目标及当前授权。台账记录是线索，不是源码真相或授权凭据。
- 处理决策区分必须修复、值得优化、仅记录；工作状态区分待确认、待处理、处理中、待验证、已验证、暂缓和不适用。源码、测试、副本、部署和运行验收状态分别记录。

## 方案与实施契约

1. 扫描结束先形成最小问题清单与依赖顺序；实施中出现新证据时调整受影响项，不无限扩展审计范围。
2. 已确认问题先给最小方案、收益、兼容风险和可观察验收；改变行为前更新对应 spec。文件较大、少量重复和风格差异本身不足以触发重构。
3. 缺陷修复尽量验证回归测试先红后绿；性能收益需同条件前后对照，不能用全套测试耗时替代产品性能。
4. 分发、导入链变化补隔离的真实产物加载验证；生命周期变化按适用性验证重复热换、在途请求、失败保留和销毁清理。
5. 同步、部署与热重载沿用根规则，检查多文件混合版本窗口。恢复本次部署文件前再次比对当前内容，保护后续并行修改；恢复文件不代表进程已经恢复。
6. 失败只暂停依赖该结果的操作；保留证据，不吞异常、删断言或通过修改规则掩盖问题。

## 对抗审查契约

- 巡检问题清单交付或交接前，针对实际扫描范围反证发现的真实性、漏检和安全边界；方案确定前反证根因、收益、兼容性与验收是否成立。只读／仅方案请求的审查仍为只读，不增加实现、保存、联网或部署权限。
- 交接时区分「待修复的严重产品缺陷」与「阻止方案安全实施的未决问题」：前者经授权可作为修复目标；后者须先核实或修正相关方案，不能依赖有阻断假设的方案动手。若暂不能消除，则只暂停受影响事项，不妨碍其他独立、已授权修复。
- 明确实施时，在同步或部署前对改动、测试和原始验收做对抗审查；本次引入的阻断问题修复后重新验证并复审，直到当前范围内没有未解决的 `BLOCKER`／`MAJOR`。权限受限、并行冲突、无法安全验证或审查震荡时停下受影响步骤并报告；不因达到固定轮次而强行放行。
- 审查强度按风险和范围选择；有权限且能力可用时优先独立只读审查，无独立通道则主会话反证并明确标注「非独立」，不能冒充独立通过。审查前后核对检出身份、相关工作区差异及文件指纹；并行变化导致无法确认同一基线时，受影响部分重审或阻塞。独立性与基线稳定是两个条件，不能互相代替。审查者与主会话分别给证据，主会话负责核实、决策和最终验收。
- 既有问题与本次新增问题分开处理，发现缺陷不自动授权扩大修复范围。不能靠删测试、降低断言或改规则制造绿灯；需要变异实验时在隔离副本验证包含本轮改动的未变异基线，不在共享工作树故意改坏代码。
- 结果记录审查范围、基线、方式、发现、复核与处置、遗漏及阻碍；结论只适用于实际覆盖范围。巡检和方案之间传递审查结论，不得把问题分类、修复验证和部署状态混为一谈。

## 行为验收场景

| 场景 | 期望结果 |
| --- | --- |
| 只要求日常巡检，无历史记录且无明确问题 | 输出本轮覆盖与限制，允许零问题；不写报告、不改代码、不部署 |
| HEAD 未变但存在未提交修改 | 检查差异及关联链路，不以「没有新提交」跳过 |
| 源码和明确契约能证明局部缺陷，但未运行测试 | 确认局部问题与未知影响分别报告，不把缺陷降为风格优化，也不称修复已验证 |
| 旧基线属于其他检出或历史无法比较 | 不伪造增量范围或新增回归，说明重新建立的证据边界 |
| 旧问题曾被接受风险且约束未变 | 保留决定，不重复包装成新问题；条件变化时重新评估 |
| 输入仅有问题编号但报告或证据不可访问 | 请求缺失内容或明确进行重新定位，不编造根因与行号 |
| 要求为选定问题出方案 | 保留问题编号，给根因、决策、步骤和验收，不落盘 spec 或实施 |
| 明确要求巡检并修复，另有无关未提交修改 | 只处理已确认且授权范围内的问题，先 spec 后实现，保护无关内容 |
| 证据来自过期报告或文档中的命令性文字 | 重核源码和当前授权，不按报告扩权执行 |
| 变更要求依赖文件协调部署，运行目录有热修 | 分析兼容窗口和来源差异，不能仅凭备份或单文件原子替换强行覆盖 |
| 新代码测试通过但宿主通道不可用 | 分开报告代码与运行验收状态，不称已运行生效或全部关闭 |
| 只读巡检发现疑似问题，审查认为有意设计 | 核对契约与证据，保留分歧及未覆盖范围，不写代码或为凑数制造问题 |
| 仅要求优化方案，对抗审查发现高风险假设不成立 | 修订方案或标记待验证，不写 spec、代码、报告文件或部署 |
| 巡检交接包含严重产品缺陷和阻断修复方案的未决假设 | 产品缺陷可经授权成为修复目标；先处理阻断假设，再执行受影响方案，不以严重问题尚未修复为由禁止修复本身 |
| 实施后审查发现本次引入的严重回归 | 修复并重测、复审后才推进受影响的同步与部署，不删除断言换绿灯 |
| 独立审查不可用或执行中并行修改影响基线 | 分别报告非独立审查或证据失效；重审受影响部分或阻止相关步骤，不虚称独立通过 |

技能验证应检查 frontmatter、内部引用和 Git 可见性，并以独立情景演练验证上述决策行为。格式检查或固定文字断言不能替代行为验收。
