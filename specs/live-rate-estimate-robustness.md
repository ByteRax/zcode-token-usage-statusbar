# 生成速度估算的鲁棒性（实时估算只计真实生成）

## 背景

状态条「生成速度」格在生成中显示估算值 = `turn-stats.js` 的 `characterRate`（字符/s）÷ `charsPerToken`（字符/token，上一完成轮自校准，缺省 2）。`characterRate` 是 2 秒滑动窗口内的字符增量 ÷ 跨度。窗口里只要混进「不是这段时间生成的字符」，估算就冲高，窗口滑过后才回落。

2026-11-25 真机实证（macOS、ZCode 4.0.0，issue #483，维护者本机在来回切换会话时复现）：

- 切换会话必重挂：主会话实例新建 tracker，`charsPerToken` 回到 null，估算改用默认比例 2。
- 冷会话新建 tracker 的首个快照是尾 60 行；窗口随后一步从 60 行回填到 288 行。
- 被压住的增量帧成批涌入：71ms 内 43 个 seq。
- 稳态通知间隔 17–250ms：页面可见、会话正常生成时量到（同一次探针，数千条通知，最小 17.4ms）。这是那一台机器的实测值，不是宿主保证。
- 单纯隐藏窗口、主线程卡顿 3 秒，都不产生这类增长。
- 单次处理 ≥8ms 的会话走通知处理预算（specs/perf-lag-reduction.md 规则 12）：间隔内的通知合并成一次入库，补齐突发在这种会话里只剩一条。
- 字符数下降（行文本变短、行被移除）在本机 5233 条通知里零出现；报告者把它列为原因之一，并注明是推测。规则 3 是按这个推测做的防御。
- 假时钟模拟（真实 300 字符/s；通知间隔 40–250ms，缩水节奏与缩水量固定或随机，共约 1500 个场景）：main 上的实现在「缩水 300 字符后回填、通知间隔 100ms」的 200 个场景里，读数平均绝对误差约 300，最高冲到真实值的 6 倍；本规格的保持窗在全部场景里读数平均绝对误差不超过 0.2。模拟不是真机取证。

## 规则

1. **不是这段时间生成的字符不进速率分子。** tracker 为每一行记住「不算新生成的字符数」：
   - 此前没见过、且行号小于该轮已知最大行号的行，是宿主往前补拉的历史（`loadOlder`、尾窗截断后的补拉）：按它出现时的长度不算。首个快照里行号乱序的行也照此处理，速率只看增量，等同于全部计入。
   - 出窗之后又回来的行不算新生成：回来时行号仍小于该轮最大行号的，按回来时的长度不算（出窗期间长出来的部分也不当作刚生成的）；否则按出窗时记下的长度不算。之后多出来的部分照常算。出窗时记的长度取「此前记录」与「出窗时长度」中较大的一个：首个快照里被当作旧行的行在窗内长出来的部分当时已经算过，回来时不再算第二遍。

   `totalCharacters`（校准分子）照常计入全部字符，校准比例不受影响。
2. **重挂后的补齐突发重取基线。** 重挂时 tracker 的首个快照是订阅那一刻的整份快照，被压住的增量帧随后涌入，两者之间的输出不是这几十毫秒里生成的。
   - tracker 建立后 300ms 内，每一帧字符增长的入库都改作新基线，逐条入库与合并入库一视同仁。不按帧间隔判：按间隔判会漏掉来得稀一点的帧。稳窗内按正常节奏来的帧也会重取基线，代价只是首个读数晚到建立后约半秒，数值不变。
   - 昂贵会话（通知处理预算把间隔内的通知合并成一次入库）的第一个合并入库可能落在 300ms 之后：建立后 1.2 秒内（预算间隔上限 1 秒，再加一次读取的耗时），第一个字符增长的合并入库也改作新基线，每一轮每次建立只做一次，之后的合并入库照常计入。这条只覆盖单次处理耗时不到 200ms 的会话：单次耗时更大的会话，第一个合并入库落在建立后 1000ms 加一次读取耗时之后，出了稳窗。稳窗内已经因合并入库重取过基线的，那一次放宽不再使用。

   稳窗从 tracker 建立起算。换会话、换纪元和 `clear()` 都视同建立，稳窗与那一次合并入库的重取重新起算。某一轮的全部行出窗后又回来，按新一轮重新计。
3. **字符数下降后沿用它下降前的速率一个采样窗（2 秒）。** 该轮的字符数比上一条快照少（行文本被替换得更短、行被移除、快照整体替换）就是下降：清样本，保持窗从这一条快照重新计时，窗内不采样。保持窗内再次下降照样续期，所以随后的回填不管隔多久都不会被采样。
   - 沿用的速率取到末样本时刻，且只在末样本停更不超过 500ms 时取：输出已经停了一阵才来的下降，保持窗内为空，不把旧速率再延长 2 秒。
   - 新基线还不满 200ms 时取不到下降前的窗口速率，就沿用上一段保持的速率（它的窗结束不到 400ms）。保持窗内再次下降而窗内没有样本时也一样，不看输出停了多久。
   - 窗内与窗结束后 400ms 内都沿用（下一条通知通常马上就来），不闪「思考中」。窗过后的首个快照作新基线；只要新基线还不满 200ms，就继续沿用。
   - 窗结束 400ms 之后才等来首个快照的，保持作废：它只作新基线，不回显下降前的速率。
4. **校准比例按会话跨重挂延续。** `charsPerToken` 的最近一次校准按会话 sid 记在模块级。重挂（切会话、store 换代）新建 handle 时沿用，没有记录才用默认值 2。

## 不变的约定

- 采样窗 2 秒、最短 200ms、停更 2 秒判陈旧。
- 稳窗之后（300ms；合并入库放宽到 1.2 秒），中断后的单次合并快照、积压通知同刻涌入，都是真实生成的迟到投递，仍按窗口平均计算。这些帧带的是新行号，也不会让字符数下降，不满足规则 1 和规则 3 的触发条件。
- 通知处理预算本身不变：廉价会话逐条同步处理，昂贵会话照旧合并。
- 完成态速率恒 null；校准仍只用本轮完成时的 `totalCharacters ÷ outputTokens`。
- 子代理槽位（`sl.calib`）不跨重挂延续，不在本规格范围。

## 已知限制

- 300ms 与 1.2 秒两个数来自一台 Mac 的实测和通知预算的公式，不是宿主保证。补齐突发如果在建立 300ms 之后才到（比如重绑后的渲染把主线程占住更久的机器），逐条入库的会话不被覆盖；合并入库条款只覆盖单次处理耗时不到 200ms 的会话，而且稳窗内的合并入库重取过一次就不再放宽。
- 新绑定或新一轮开始后 300ms 内出现字符下降、此前又没有可沿用的速率时，保持窗内为空，首个读数要等到约 2.3 秒之后。
- 字符数下降的前提没有在真机证实，规则 3 是按报告者的推测做的防御。窗口里有没被重取基线的补齐样本时又缩水，沿用的会是那个被抬高的值，持续一个保持窗。
- 2 秒滑动窗口对真实生成的突然加速同样会显示成冲高、约 2 秒回落，这是算法固有行为。

## 验收场景

| 场景 | 期望 |
|---|---|
| 稳定流中窗口一次前插 5000 字符的旧行 | `characterRate` 不变；`totalCharacters` 含旧行 |
| 出窗的行（5000 字符）原样回来，其间别的行照常增长 | 回来的不算新生成，读数只含别的行的增长；`totalCharacters` 含它 |
| 先出窗的行在最大行号回落之后回来 | 同上 |
| 出窗的行回来时比出窗时长 | 按回来时的长度不算，出窗期间长出来的不计入 |
| 出窗的行回来时比出窗时短 | 不倒扣，也不算一次新的下降 |
| 首快照里被当作旧行的行在窗内增长，出窗后以最大行身份回来 | 窗内算过的增长不再算第二遍，只算出窗后新长的 |
| 出窗的行以大于最大行号的行号回来，且回来时更长了 | 只算它出窗后长出来的 |
| 新 tracker 首快照后 10ms、20ms 各增 300 字符，之后 300 字符/s | 首个读数按 20ms 处的基线算，是 300 |
| 首快照后 20ms 才来第一帧补齐（增 300 字符），之后 300 字符/s | 是 300 |
| 稳窗内按 100ms 间隔的正常帧 | 每帧都重取基线，首个读数从稳窗内最后一帧起算 |
| 建立 10ms 处字符持平的一帧 | 不动基线 |
| 建立 299ms 处的一帧增长 | 重取基线 |
| 建立整 300ms 处的一帧增长 | 按窗口平均 |
| tracker 建立 800ms 后积压帧以 10ms 间隔涌入 | 仍按窗口平均 |
| tracker 建立 3 秒后积压帧以 10ms 间隔涌入 | 仍按窗口平均 |
| 时钟从 5,000,000ms 起，建立后 10ms 突发 | 稳窗照样生效 |
| 昂贵会话（预算间隔 72ms）：补齐帧被合并成一次入库，之后 300 字符/s | 读数是 300 |
| 昂贵会话（预算间隔 360ms）：第一个合并入库落在建立后 400ms | 重取基线，只做一次 |
| 字符持平的合并入库 | 不占用那一次重取基线 |
| 合并入库第一次带来新一轮 | 入库不抛错 |
| 一次合并入库里两轮同时带着补齐的增长 | 两轮都重取基线，各记各的那一次 |
| 合并入库落在建立后 1199ms | 重取基线 |
| 合并入库落在建立整 1200ms | 按窗口平均 |
| 预算间隔到上限 1 秒的会话：第一个合并入库落在建立后 1150ms | 照样重取基线 |
| 昂贵会话：建立 5 秒后才有合并入库 | 仍按窗口平均 |
| 廉价会话：建立 500ms 后同步入库两次，先慢后快 | 按窗口平均，不重取基线 |
| 昂贵会话：尾部定时器迟到，期间跳过了通知，之后走同步路径带着补齐的 600 字符 | 按合并入库论，重取基线 |
| 建立 5 秒后换会话、换纪元或 `clear()`，10ms 后补齐突发 | 按新基线算，是 300 |
| 一分钟后切到另一个会话，补齐突发同样被合并成一次入库 | 稳窗与那一次合并入库的重取重新起算 |
| 稳定流缩水 300 后 100ms 回填 | 读数保持下降前的值 |
| 缩水后不再回填 | 保持窗内是下降前的值，之后按新基线 |
| 输出停了近 2 秒之后才缩水 | 读数为空，不沿用停更前的速率 |
| 上一段保持的窗结束 950ms 后又缩水，末样本已停更 750ms | 读数为空，不借用上一段保持的速率 |
| 保持窗已结束、下一条通知还没来（窗结束 200ms 内） | 读数不空 |
| 保持窗结束 399ms 后才有下一条通知 | 读数不变，中间不出现空值 |
| 保持窗结束整 400ms，之后才有下一条通知 | 保持作废，读数为空 |
| 保持窗结束 1.5 秒才有下一条通知 | 读数为空，不回显下降前的速率 |
| 保持窗结束的那条快照恰好又缩水，100ms 后回填 | 保持窗续期，回填不被采样，读数不变 |
| 保持窗内再次缩水，150ms 后才回填 | 同上 |
| 新基线不满 200ms 时又缩水 | 沿用上一段保持的速率，不出现空读数 |
| 该轮完成（窗口里有样本，或完成的同一条快照里字符数下降） | 估算为 null，完成态照常 |
| 上一轮校准出 3 字符/token，切走再切回，新轮 9 字符/s | 格面 3.0 t/s |
| 随后一轮校准出 4 字符/token，再切走切回，新轮 8 字符/s | 格面按 4 算，2.0 t/s |
